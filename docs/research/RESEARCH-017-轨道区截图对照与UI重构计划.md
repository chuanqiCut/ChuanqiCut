# RESEARCH-017 — 对标 App轨道区截图对照与 UI 重构计划

> 命题（传哲 2026-10-13）：「先看下对标 App的轨道区截图，看下你能至少做成这个样子的吗，然后写一份 UI 重构计划」
> 材料：6 张对标 App iOS 真机截图（素材库 1 张 + 编辑页 5 张：默认态 / 主轨选中态 ×2 / 音频多轨态 / 音乐添加态）
> 归属：A 线（编辑器/UI）；上游：RESEARCH-008（范式）/ RESEARCH-013（轨道优化路线）/ RESEARCH-010 §6（分端形态）
> 结论先行：**能做到。** 骨架（三区 / 标尺 / 缩略图 / 中央播放头 / 两级工具栏 / 分割·删除·裁剪）已落地，
> 差距集中在**视觉保真层与轨道区信息架构**，绝大部分是纯 UI 工作，不依赖内核新能力。

## 3. 重构前置项（RESEARCH-013 §4.1 遗留的 P0，必须排在视觉批之前）

**双份时间轴实现仍是红线边缘**：SwiftUI `EditorTimelineView(423行)` 与 UIKit `EditorTimelineUIView(469行)`
的命中/commit 逻辑是两份（UIA-039/040 每次都双写两处）。按 RESEARCH-013 §5.1 抽
**`TrackInteraction` 纯逻辑 reducer**（输入=归一化手势事件，输出=渲染态+待提交命令），
两个展示层只做翻译与自绘。**不先做这一步，下面每个视觉批都要双写一遍。**

与 EDIT-012（B5.5，commit/done 双层）的关系：reducer 是 UI 侧事件收敛，EDIT-012 是内核侧提交通道；
reducer 输出的"待提交命令"在拖拽中走 PreviewSync、松手走 Execute —— 二者在 B5.5 会师，互不阻塞。

## 6. 数字纪律

- 现状核验为代码事实（文件与行号可复验）；截图要素为**视觉转述**，验收以"复刻形状走查清单"为准，
  不承诺逐像素一致（同 RESEARCH-008 §7）；
- **本节更正版 2026-10-13（纠 §2 S3 行，留痕不改原意）**：
  首版写「S3 选中态视觉 ❌ 无选中视觉层（grep selected/handle 零命中）」——**此结论为假阴性导致的误判**。
  事实：白描边在两侧均已实现（UIKit `TimelineContentView.applySelectionBorder` L330-340、
  SwiftUI `EditorTimelineView.draw` L362-372，均为 `Theme.primaryText`(=白) lineWidth 2）。
  **根因 = P126 复发**：当时用 Grep 工具搜 `selected\|handle`，而该工具底层是 ripgrep（Rust 正则），
  `\|` 是**字面竖线**而非「或」，于是零命中。**教训（上升到纪律）**：检索工具报 0 命中时，
  必须先怀疑工具语义、再怀疑代码缺失 —— 分两个关键词各查一遍交叉验证，确认后再下结论。
  真正缺失的只有「左右把手」与「片段中央时长数字」两项。
- 把手尺寸/配色等为 [E] 估算，以 U1 问卷真机走查校准；
  ⚠️ U1 开工实测：`TimelineLayout.trimHandleWidth = 8`pt（手势判定宽度），与本文 [E] 估的 8pt 巧合一致 ——
  U1 把手**沿用同一常量**，保证「看到的把手」=「按得中的热区」（这是唯一值得说的话）。
- 本计划不含性能数字；U0 完成后回填"双实现消除"的回归证据（`swift test` 用例数）。
