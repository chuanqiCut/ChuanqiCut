# ADR-0007：HarmonyOS 作为可选项，本期只做架构预留

- **状态**：提案（待批准）
- **日期**：2026-09-23
- **相关**：ARCH-004 §5

## 背景

需求：鸿蒙"作为可选项，目前不支持，但架构要预留"。

可行性核验结论：**HarmonyOS NEXT（API 12+）具备承载本项目所需的全部关键能力**：

| 能力 | 状态 |
|---|---|
| 图形 | 原生 Vulkan 1.3 + OpenGL ES 3.2；`XComponent` 提供原生渲染 surface（`OHNativeWindow`） |
| 硬解/硬编 | AVCodecKit（`OH_VideoDecoder` / `OH_VideoEncoder`），H.264/H.265/HEVC 10bit，Surface 模式支持零拷贝 |
| 解封装/封装 | `OH_AVDemuxer` / `OH_AVMuxer`（仅 C 接口） |
| 音频 | OHAudio |
| 原生桥接 | NAPI（C/C++ ↔ ArkTS） |
| UI | ArkUI (ArkTS) |
| 工具链 | DevEco Studio + Hvigor + CMake，产物 `.hap` |
| 推理 | MindSpore Lite |

已有第三方引擎以「ArkTS 壳 + XComponent + Vulkan + NAPI」的方式完成原生移植，验证了链路可行。

已知限制：软解当前仅支持 H.264（其余需 FFmpeg 兜底）；生态与机型覆盖仍在早期。

## 决策

鸿蒙定为 **P2 / 可选**。本期：

**做（低成本预留）**
1. PAL 接口定义覆盖鸿蒙所需能力（已在能力查询枚举中体现，不写任何 `#if OHOS` 特化）。
2. `pal/ohos/` 目录占位，含**接口编译检查 target** —— 保证 ohos PAL 与接口签名同步演进，防止架构腐烂（这是预留能否兑现的关键）。
3. 依赖清单登记鸿蒙平台的库形态与协议（ARCH-002 §7）。
4. 任务清单保留 `OHOS-0xx` 组，**不排期**。
5. 编码全程遵守"内核不得假设 Apple/Android 特性"的约束（由 PAL 抽象与能力查询强制）。

**不做（本期）**
- 不实现鸿蒙 PAL 代码
- 不搭建 DevEco 工程 / 不做机型适配 / 不做测试

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 本期一并实现鸿蒙 | 资源不足；机型覆盖与生态成熟度风险高；会拖慢 P0/P1 |
| 完全不考虑鸿蒙 | 若未来要做，需在 PAL 与能力查询上做返工；预留成本很低，不预留不划算 |

## 后果

**正面**
- 未来启动鸿蒙时，因内核与效果 100% 共享，工作量集中在 PAL + UI 壳，显著低于任一端的首次实现
- 接口编译检查保证预留不腐烂
- 本期几乎零成本

**负面 / 风险**
- 只做接口编译检查不能保证真实可行性（工具链、权限、性能都未验证）
- 若鸿蒙的某个 PAL 能力实际不可用，可能需要调整 PAL 接口定义，影响已完成的 Apple/Android 实现

**缓解**：若未来启动，第一步必须是 `OHOS-001 环境验证`（DevEco + NDK + Vulkan 清屏 + AVCodecKit 解一帧），验证通过后才投入后端实现。

## 反转条件

- 需求明确将鸿蒙提升为 P1 → 重新排期并按 §"若启动路径"执行；
- 需求明确永久取消鸿蒙 → 删除 `pal/ohos/` 与 `OHOS-0xx` 任务组。

## 落地任务
`OHOS-001`（仅接口编译检查，低成本），其余 `OHOS-0xx` 未排期
