> RESEARCH-014（RENDER-001 装配器已随 B0 落地）、ADR-0034（地基先行 / 严禁临时方案）、
> ADR-0039（`Chq` 命名前缀）、红线 #4（有理数时间）、红线 #9（预览与导出同一张图）

## 背景

RESEARCH-016（2026-10-13）逆向 `/Users/zhuning/Documents/test/` 下对标平台/对标 App iOS 编辑 SDK
（7 模块 / 1335 头 / 78808 行），比对出本仓 `ChqClip`（`engine/core/cq/model/chq_timeline.h:44-62`）
相对对标平台 `其轨道槽位模型` 的**结构性缺口**：

| 能力 | 对标平台 其轨道槽位模型 | 本仓 ChqClip | 影响的功能批次 |
|---|---|---|---|
| 空间变换 | `transformX/Y/Z · rotation · scale · mirror` | **无** | B6 贴纸定位、B7 画中画 |
| 渲染层级 | `layer(0~1000)` | **无**（靠数组顺序） | B7 多轨叠放 |
| 变速 | `speed`（Track 还有 `absSpeed`） | **无** | B7 变速 |
| 关键帧 | `keyframes[]`（关键帧即 Slot 副本） | **无** | B8 关键帧动画 |
| 相对布局 | `relativeWidth/Height` | **无** | 改画布比例时子元素漂移 |
| 音量/变声 | `audioFilter` | 仅 `track.muted` 布尔 | B5 片段音量 |

**问题**：RESEARCH-010 §5.2 的批次表（B0~B8）**没有任何一批为上述数据立地基**。
B0 只立了 RenderGraph + 属性系统 + Portable shader。若照原排期推进，到 B7 做变速/画中画时
才会在上层补这些数据 —— 那时 B6 文字贴纸已写完，属于 ADR-0014 那类「两套拼起来的返工」。

另有一条机制缺口（RESEARCH-016 §2.1）：对标平台把「渲染同步点」(`commit`，高频、触发 diff、
不入 undo 栈) 与「撤销事务边界」(`done`，两次之间合成一条 undo) 分成两层。
本仓 `ChqCommandHistory::Execute` 三件事合一（改模型 + 入 undo 栈 + 触发刷新），
「拖拽结束只提一条命令」目前是**靠纪律而非靠机制**保证。

## 决策

### 1. 插入新批次 **B5.5「空间与交互地基」**，位置在 B4 之后、B6 之前

修订后拓扑：

```
B0 渲染地基 ✅已提交（问卷未回收，未标记完成）
B1 模型命令 ✅已完成
B2 音频地基 ┐
B3 持久化 ─┤（建议排到 B5.5 之后，见 §3）
           └─ B4 导出闭环 ← B0 + B1        【第一个可见出口】
                └─ B5 音频可见 ← B2 + B4
                     └─ ★ B5.5 空间与交互地基 ← B4
                          └─ B6 文字贴纸 ← B0 + SHADER-001 + B5.5
                          └─ B7 视觉效果 ← B0 + B5.5（变速/画中画要用 speed/transform/layer）
                               └─ B8 进阶 ← B7（关键帧要用 keyframes）
```

**为什么放这里而不是 B4 之前**：B4 导出闭环不依赖空间数据（导出单轨视频不需要画中画/变速），
把它放在 B4 之后可以**不推迟第一个可见出口**；同时它仍在依赖它的 B6/B7 之前，
满足 ADR-0034「地基先于依赖它的功能」。

### 2. MODEL-004：空间变换、层级、变速、关键帧数据槽

新增 `ChqTransform`（遵循 ADR-0039 的 `Chq` 前缀），挂到 `ChqClip` 与 `ChqTrack`：

- 位移 `translate_x/y`：**归一化到画布**，原点与方向沿用既有约定（`CIContext` 显式 gamma sRGB
  与「检测坐标左上原点归一化」已成文，不得另立一套坐标语义）
- `scale`、`rotation`、`mirror`（0 正常 / 1 水平 / 2 垂直）
- **相对尺寸** `relative_width/height`（相对 parent），配合画布比例切换时同步修正
  （对标平台对应方法是 `setCanvasRatioWithUpdateRelativeLocation:`，注释明说不同步修正
  「子元素会错乱」—— 本仓 `ChqSetCanvasCommand` 必须回答同一问题）
- `layer`：**显式渲染层级整数**，不得继续用数组顺序表达叠放

同时给 `ChqClip` 补 `speed`（变速）与 `keyframes`（关键帧数据槽）。

**关键帧粒度取属性子集，不取整个 Clip 深拷贝** —— 对标平台为了让任意属性自动获得关键帧能力，
让关键帧直接克隆整个 Slot（`其轨道槽位模型+iOS.h:161` `createKeyframe`），代价是内存膨胀。
本仓已有属性袋（`chq_property`，MODEL-003），做**按 key 的属性快照**更省且更好做插值。

### 3. EDIT-012：commit/done 双层提交（PreviewSync 通道）

- 在 `ChqCommandHistory` **之上**增加一条独立的预览同步通道：
  拖拽/滑块等连续操作走 `PreviewSync`（只 diff → 渲染，不入 undo 栈），
  操作结束走 `Execute`（入 undo 栈）。
- **二者必须共用同一个 diff 出口** —— 这条是硬约束，违反即形成第二套渲染路径
  （ADR-0014 的坑不得再踩）。
- 保留现有 Command 增量路线，不改为对标平台的整模型快照（见 §5）。

### 4. B3 持久化建议排到 B5.5 之后

B5.5 会给 `ChqClip` 加一批字段。若 B3 先做，序列化格式要改第二遍。
**若因故提前做 B3，则序列化层必须做成可扩展**（版本号 + 未知字段跳过），不得写死字段集。

## 5. 明确不采纳（对标平台做法，逐条给理由）

| 对标平台做法 | 不采纳的理由 |
|---|---|
| 整模型快照式 undo（`其提交接口` 持有完整 `其数据模型`） | 本仓已选增量 Command；快照换来「新功能自动获得 undo」，代价是每次提交的内存与 diff 开销。增量路线要求每个命令写对 Undo，成本已知且可控 |
| 双数据模型（`其数据模型` + `其播放数据层` + 转换器） | 每加能力改两处 + 转换器。本仓 C++ 单一模型，不引入等价物 |
| 预览/导出两条管线 | 与红线 #9 冲突，**本仓更先进，不动摇** |
| 浮点秒时间 / 注释与类型矛盾（`splitFromTime` 注释写微秒实为 `NSTimeInterval`） | 红线 #4 已有理数时间，比他们严格，保持 |
| 用标量 BOOL 表达多状态机（`其播放器状态枚举` 5 态 → `BOOL playing`） | 见 Pitfalls 记录：丢掉的是两个「请勿进行操作」状态。**跨层签名枚举必须具名，异步必须有完成回调** |

## 6. 代价（明确接受）

- 用户可见的文字贴纸（B6）与视觉效果（B7）因此各推迟一批次。
- `ChqClip` 字段增加会影响序列化（B3）与 C ABI（若需对外暴露）的面。
- B5.5 自身改动 `chq_timeline.h/.cpp` 与 `chq_command.h/.cpp`，属高冲突文件，由集成机承接。
