# ADR-0013：预览取帧的线程归属与共享命令队列

- 状态：已接受（2026-10-04，UIA-010 子步骤 5 落地）
- 关联：`ADR-0011`（core 调 PAL 工厂的隔离规则）、`ADR-0012`（命令提交时机与线程边界）、
  `TASK-UIA-010`、`.ai/modules/preview.md`
- 影响面：`core/preview/*`、`core/gfx/*`、`pal/*/gfx`（新增 `ICommandQueue::NativeHandle`）、
  `bindings/swift`、`apps/apple/packages/SharedUI`

## 背景

UIA-010 子步骤 1~4 落地后，播放是这么跑的：

```
主线程 Timer(30Hz) → player.tick() → setPlayhead → SwiftUI body 重算
                                     → MTKView.setNeedsDisplay → draw(in:)
                                     → preview.renderFrame(pts)   # seek+解码+导入+离屏绘制
                                     → blit 进 drawable + present
```

`renderFrame` 是**同步**的，谁调用谁承担全部耗时。实测（Debug，256x256）单帧
`total ≈ 96ms`，其中取帧段 90ms —— 即主线程每帧被堵近百毫秒（红线 #8「主线程零阻塞」
直接被违反）。

## 决定

### D1：取帧/渲染搬到泵线程，主线程只 blit + present

新增 `core/preview/preview_pump.{h,cpp}`：`PreviewPump` 拥有**一条**线程，串行执行
`IPreviewFrameSource::RenderFrame`。主线程只做两件事：

1. `Request(pts)` —— 入队 + 通知，不阻塞；
2. `Lock() → LatestLocked() → blit → Unlock()` —— 取已完成帧并拷贝进 drawable。

**为什么是内核拥有这条线程**（而不是 UI 层用 GCD 队列）：
不是 UI 逻辑（红线 #1 下沉）；三端 UI 不必各自重写一套泵；且能被 C++ 单测覆盖
（注入假帧源，把并发语义测成确定性断言，不需要 Metal / 解码后端）。

这与 UIA-010 的 D2「时钟不跑线程，线程决策归上层」**不冲突**：D2 约束的是
`PlayerClock` 这个纯计算对象；而泵是**可选组件** —— UI 决定要不要建它，不建就沿用
旧的同步路径。

### D2：渲染器自此**只属于泵线程**（硬约束，不是建议）

挂上泵之后，任何线程再调 `cq_preview_render_frame` / `cq_preview_resize` 都是数据竞争：
解码会话与 `CVMetalTextureCache` 都不可并发访问。此约束已写进
`preview_renderer.h` 与 `cq_sdk.h`，不是"口头约定"。

推论：`Resize` 会销毁离屏 RT，故**只能**经 `PreviewPump::RequestResize` 在泵线程执行；
消费端取句柄必须走 Lock/Unlock 协议（持锁期间泵不会发布新帧、不会 resize）。

### D3：请求合并（coalescing）—— 取最新，丢中间

请求速率 > 渲染速率时必须丢帧，否则队列无界增长。新请求直接覆盖未被取走的请求，
被覆盖者永不被渲染（计入 `Stats::coalesced`）。时刻由墙钟算（`PlayerClock`），
丢帧只让画面少几张，**不会**让播放变快或变慢。

⚠️ 这与 UIA-005 明确**拒绝**的「命令合并」是相反的决定，理由是相反的：那里合并会
丢掉用户的一次编辑（撤销栈必须有这条记录）；这里合并丢的是"某一时刻的画面"，
而画面是时间的函数、重算即得。

### D4：UI 侧的 blit 必须复用**内核那条命令队列**

泵线程写离屏 RT、UI 线程读它。Metal **只保证同一条队列内**命令缓冲按 commit 顺序
执行；跨队列的资源先后需显式同步（`MTLSharedEvent` / `MTLFence`）。

故：

- `gfx_device.cpp` 由「每帧 `CreateCommandQueue`」改为**按设备复用一条**；
- 新增 `ICommandQueue::NativeHandle()`（中性句柄）与 `IGfxDevice::SharedQueueHandle()`，
  经 `cq_preview_shared_queue()` 给到 UI；
- `PreviewFrameRenderer`（SharedUI）用它建命令缓冲，不再自建队列。

顺带收益：原来每帧新建一个 `MTLCommandQueue` 是纯无谓开销。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 双缓冲 / 多 RT 轮换 | 需要 `PreviewRenderer` 支持多目标，改动面大；共享队列已能保证顺序，单 RT 足够 |
| 主线程与渲染互斥（Lock 包住整帧渲染） | 主线程会在锁上等到一帧结束（实测近百毫秒），等于把阻塞换个形式保留下来 |
| 消费者 ack（泵等主线程消费完再渲染下一帧） | 主线程 blit 不 wait，GPU 上仍有并发窗口；且会把泵吞吐压到消费速率 |
| 泵放 UI 层（GCD 队列） | 三端各写一遍；并发语义无法用确定性单测覆盖（依赖真实 Metal + 解码） |

## 后果与已知限制

1. **帧率不因此提高**。帧率上限仍是 `1/单帧取帧耗时`。本次换来的是主线程不再被
   每帧堵住（UI 响应），不是"播放变快"。
2. **真正的帧率瓶颈已定位在取帧策略**：顺序播放时每帧都走 `SeekPolicy::kExact`，
   即每帧都重新 seek 到关键帧并解码整个 GOP。实测 Debug 1280x720 播放 1s 只出
   3 帧。修复属 MEDIA-020 的顺序解码路径，**不在本 ADR 范围内**（见
   `docs/tasks/TASK-MEDIA-021.md`）。
3. 消费端持锁期间**不要**阻塞等待（如 `waitUntilCompleted`），也**不要**调
   `Request` —— 后者会与锁死锁（第一版测试实踩）。
4. 暂停/拖拽场景靠 MTKView 的「自驱重绘」追帧（有次数上限，防渲染持续失败时以
   vsync 频率空转）。
