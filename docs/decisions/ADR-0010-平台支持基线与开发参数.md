# ADR-0010：平台支持基线与开发参数

- **状态**：已接受（2026-09-25，传哲拍板）
- **相关**：ARCH-001、ARCH-004、ADR-0008

## 1. 最低系统版本

| 平台 | 最低版本 |
|---|---|
| iOS | **16** |
| macOS | **15.4** |

- 该基线**此前未写进任何文档**，而 Apple 端每个任务都会反向被它约束，故在此固化。
- macOS 15.4 是较高门槛（Sequoia 系列），对应的用户覆盖面窄于常见的 macOS 12/13 基线。
  此为项目初期「以开发机为准、先跑起来」的选择；
  若后续需要扩大桌面端覆盖，应另立 ADR 下调，并复核所用系统 API 的可用性。
- 影响面：决定可用的 Metal 版本、AVFoundation / PhotoKit / VideoToolbox 特性集。
  Apple 侧任何新代码开工前，都应对照本基线确认 API 可用性。

## 2. FFmpeg 的授权档位（重要，勿误读）

### 传哲的明确要求（2026-09-25）

> 「FFmpeg 理论上可以先**不使用 GPL 相关的代码**，**保持 LGPL** 的能用。」

即：**排除 GPL，停留在 LGPL**。这与本项目已构建的产物**完全一致**，无需改动。

### 当前产物的实际授权状态

| 项 | 值 | 含义 |
|---|---|---|
| `manifest.license` | `LGPL-2.1-or-later` | 不是 GPL |
| `CONFIG_GPL` | `0` | **不含任何 GPL 代码** |
| `CONFIG_LGPLV3` | `0` | 也不是更严格的 LGPLv3 |
| `CONFIG_VERSION3` | `0` | 无 v3 系条款 |
| `profile` | `demux` | 仅 demux/parser/bsf，从 `--disable-everything` 逐项开启 |

构建方式为 `--disable-everything` 后只显式开启 demux/parser/bsf，
**从未启用任何 GPL 组件**（无 libx264/libx265/postproc 等）。

### ⚠️ 一处必须说清的区分：LGPL ≠ 无义务

排除 GPL 后**仍存在 LGPL 的附加义务**，这一点不要因为「只是 LGPL」就忽略：

> LGPL v2.1 对**静态链接**的核心要求是：**接收者必须能够用修改过的库版本替换并重新链接。**

因此「技术上能用」与「**可以分发**」是两件事：
- 现在能用：产物未接入构建，未链接未分发 → 义务**未触发**
- 将来要分发：仍需选一种处置方式（见下）

### 后续两条路（待法务，届时立 ADR）

| 方案 | 说明 |
|---|---|
| A 接入 FFmpeg | 维持 LGPL 档位（禁 GPL 如本节所述），并履行 LGPL 静态链接义务：提供 relink 能力 / 目标文件归档 / 商业授权 / 动态链接 |
| B 不接入 FFmpeg | demux 走平台原生：iOS/macOS 用 AVFoundation，Android 用 MediaExtractor。无 LGPL 义务 |

### 修订记录

2026-09-25 初稿曾写「传哲判断有误」——**那是 team-lead 的误读**（把「不用 GPL、保持 LGPL」
听成了「规避 LGPL」），并非传哲判断有误，已更正。技术事实本身未变。

**架构约束（因此而生）**：CORE-006 的 PAL Media 接口**不得依赖任何 FFmpeg 类型**
（不得出现 `AVFormatContext` / `AVPacket` 等）。接口必须保持抽象，
否则方案 A/B 的切换会变成跨层返工。这与既有的「头文件零平台类型」红线一致。

## 3. 容器格式支持范围

沿用已定稿的**常用子集档位**（17 demuxer / 13 parser / 5 bsf，合并产物 2.22 MiB）：

`aac aac_adtstoasc avi flac flv gif image2 image2pipe m4v matroska mov mp3 mpegps mpegts ogg pcm_s16le wav`
（含别名：mp4/3gp/m4a→mov，webm→matroska，oga→ogg）

被裁掉的 `mxf` / `dnxhd` / `r3d` / `dvdvideo` 等专业/广播容器**本期不支持**。
若未来面向专业剪辑，需另立任务与 ADR 扩回。

## 4. Android 与鸿蒙

- **Android**：接受排在 Phase 3。
- **鸿蒙**：维持现状 —— 仅 `pal/ohos/` 接口编译检查（ADR-0007），本期不实现。

## 5. 团队与协作

- **当前单人开发**，任务按单人粒度拆分，不做并行 write_set 划分。
- 后续有新人加入时，再按模块重写边界与任务拆分。

## 6. 真机验证与可观测性要求

- 参考机型：**iPhone 17 Pro**。
- **等 iOS 端能跑起来后由传哲本人实测**，不看模拟器数字。
- 因此：**日志与埋点必须先行做扎实** —— 到时直接看日志/埋点结果定位问题，
  而不是临时补埋点再复现。
  - 已具备：`Log` 分级 + 帧级 trace（CORE-003，用 `RationalTime` pts 标识帧）
  - 待补：关键路径的性能埋点（demux / decode / render / encode 各环节耗时、
    队列深度、纹理用量），并可按帧追溯
- 注意：本机为 **Intel Mac（x86_64，i7-9750H）**，**无 ANE、无 ProRes 硬编**。
  性能基线不得取自本机；须在 Apple Silicon 真机上采集（PERF-001 需标注采集机型）。

## 7. 本期不做的（已确认）

- Apple 开发者账号 / 证书：不阻塞编码，先开发，需要时再补
- golden 真实授权素材：暂缓，继续用合成素材（避免版权问题）
