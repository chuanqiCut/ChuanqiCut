# ADR-0001：采用 C++ 共享内核，UI 层各端原生

- **状态**：提案（待批准）
- **日期**：2026-09-23
- **相关**：RESEARCH-001 C3/C7、ARCH-001 §3、ARCH-005

## 背景

原调研（`技术调研_剪辑软件技术方案分析.md` §6.3）明确建议「早期不要做 C++/Rust 共享核心」，并把「不做 Android」写入了明确不做的清单。该结论的前提是**项目只做 iOS + Mac**。

需求已变更：Android 必须支持（P1），鸿蒙作为可选（P2）。在此前提下继续各端独立实现，意味着：
- 时间线模型、效果算法、序列化逻辑要写三遍；
- 三端行为一致性无法保证（同一个项目在 iOS 与 Android 导出结果不一致）；
- 缺陷要在三端分别修三遍。

## 决策

1. 建立 **C++20 共享内核**（`core/`），承载除 UI 之外的一切：时间线模型、命令与 Undo、关键帧动画、Retime、渲染图、媒体调度、音频图、效果算法、推理抽象、项目序列化。
2. **UI 层不共享**：iOS/macOS 用 SwiftUI，Android 用 Compose，鸿蒙用 ArkUI。
3. 内核对外暴露 **纯 C ABI**（`cq_sdk.h`），各端通过绑定层包装成平台惯用接口。
4. 平台差异收敛到 PAL（`pal/<platform>/`），PAL 头文件不得暴露平台原生类型。
5. **废弃 KMP**：原方案用 Kotlin Multiplatform 共享数据模型且"仅限 iOS 端"，与 C++ 内核职责完全重叠且无跨端收益。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 各端独立实现（原方案） | 前提已失效；三倍维护成本，一致性不可保证 |
| Rust + wgpu | naga→MSL 成熟度低于 SPIRV-Cross；NDK/NAPI 工具链整合成本高；团队能力不匹配 |
| Kotlin Multiplatform | 无法承载渲染与高性能算法；只共享模型无意义 |
| Flutter 统一 | 引擎渲染上下文与主 GPU 管线竞争；编辑器高频手势体验有损（另见 RESEARCH-001 F7） |

## 后果

**正面**
- 三端行为一致有结构性保证（同一份算法代码）
- Android / 鸿蒙的边际成本大幅降低（只需 PAL + UI 壳）
- 内核可在桌面环境单测，不依赖真机

**负面 / 成本**
- 前期设计成本增加约 15%（PAL 接口、ABI 边界、绑定层）
- 团队需要 C++ 能力；Swift 工程师需要跨语言调试能力
- 跨语言边界的调试体验差于纯原生，需投入工具（符号化、日志桥接）

## 反转条件

若出现以下情况之一，应重新评估：
- Android / 鸿蒙在 Phase 1 结束前被明确取消；
- C++ 内核导致 Apple 端首个可用版本的交付延迟超过 2 个迭代，且无缓解手段。
