## 1. 结论：新开会话，不要在这个会话里写代码

**理由有三条，都是成本问题不是风格问题：**

1. **上下文会被代码撑爆。** 这个会话已经压缩过一次。编码阶段单个任务动辄几百上千行代码 + 测试 + 编译输出，两三个任务就会把上下文顶满。顶满之后的表现不是报错，是**悄悄忘记前面定的红线**——比如忘了「时间用有理数」、忘了「PAL 头文件零平台类型」。这种退化最难发现。
2. **这个会话的产出已经全部落盘。** 决策在 `docs/decisions/ADR-000x`，架构在 `docs/specs/ARCH-00x`，规则在 `.ai/source/AGENTS.root.md`，任务在 `docs/tasks/`。会话本身没有独占价值。
3. **新会话不是失忆。** `.ai/` 这套东西就是为了冷启动重建而建的。新会话读同一套真源，等于带着同一套规则重新进场。

> 反面情况：**不要用新会话做架构决策或跨任务重构**。那类工作需要的正是全局上下文，成本再高也值得在一个会话里做。

## 3. 新会话开场模板（复制粘贴）

```
我要开始做 ChuanqiCut 的任务 <TASK-ID>。

开工前按顺序读完，读完复述一遍你要遵守的红线：
1. .ai/source/AGENTS.root.md（根规则，真源）
2. .ai/modules/<本任务所属模块>.md
3. docs/tasks/TASK-<ID>.md（任务卡；若不存在，先用 .ai/templates/task.md 生成给我确认）
4. docs/decisions/ADR-<相关>.md

然后，在你写第一行代码之前，先输出：
- 你的 write_set（要改哪些文件）
- 你的验证命令（编译 / 单测 / golden，具体命令）
- 你判断的主要风险

我确认之后你再动手。任务结束后必须回写 .ai/ 下相应文件，
并报告：执行了什么命令、通过/失败、跳过了什么、剩余风险。
```

**为什么要求"先输出 write_set 再动手"**：这是唯一能在写代码之前拦住返工的检查点。跳过它，最常见的后果是两个任务改同一个文件，或者写出了违反红线的代码却已经写完了三千行。

## 4. 会话切分规则

| 场景 | 粒度 |
|---|---|
| 单个实现任务 | 一个任务一个会话 |
| `CORE-006` 这类**契约冻结**任务 | 拆两个会话：① 只出头文件 → 人工评审；② 评审通过后才写实现 |
| 只读探索 / 调研 / 文档检索 | 可一会话多个（不产生 write_set 冲突） |
| 架构决策、跨任务重构 | **必须**单会话，宁可上下文吃紧 |
| 两个 write_set 相交的任务 | 禁止同会话，串行做 |

**并行边界**（写给多人协作）：适合并行的是只读探索、测试设计、日志分析、写集不相交的模块实现；禁止并行的是架构决策、共享接口设计、同一文件改写、高冲突文件（`CMakeLists.txt`、`cq_sdk.h`、`*.pbxproj`、`manifest.toml`）。

## 5. Phase 0 我建议的开局顺序（附理由）

```
会话 1  INFRA-001 + INFRA-002   目录骨架 + CMake + CTest
会话 2  CORE-001 ~ CORE-005     base 层（时间/状态/日志/内存/并发）
会话 3  CORE-006（上半）        PAL 接口头文件，出完就停，等评审
会话 4  CORE-006（下半）        评审通过后才写实现
会话 5  DEPS-001 ~ DEPS-004     manifest / lock / 协议门禁 / 符号门禁
会话 6  DEPS-010 + DEPS-013     FFmpeg demux 档位构建 + 体积符号基线
会话 7  CORE-007 ~ CORE-009     能力查询 / 线程模型 / EditorSession
会话 8  PERF-001                性能基准套件（依赖 CORE-006 冻结后才能写）
会话 9  PERF-002 + PERF-003     设备档位门禁 + 性能门禁
```

**顺序里的三个关键判断：**

1. **先让"能编译、能跑测试"存在**（INFRA-002），否则后面每个任务都只能交付"看起来对但没验证过"的代码。
2. **`CORE-006` 是整个工程杠杆率最高、也最容易返工的地方。** 它是 `core/` 和 `pal/` 的接缝，一旦定错，所有 PAL 实现全部要改。所以它**必须单独一个会话，出完头文件就停，人工评审通过才写实现**。不要为了省事把实现顺手写了。
3. **依赖治理（DEPS-001~004）要早于大量引库。** 因为后面每引入一个第三方都要过它的门禁；晚了就是补登记。

**注意一个阻塞**：`DEPS-010~012` 的**构建脚本可以先做**，但**最终链接方式定型**依赖 LGPL 处置决策（见 `.workbuddy/memory/MEMORY.md` §悬而未决）。别在没拍板前把链接方式写死进打包架构。
