# 2026-10-04

## UIA-010 子步骤 5：把预览取帧搬到泵线程（主线程只 blit）

传哲指示「先按计划继续任务，相机链路他在另一台设备并行做」→ 按计划推进子步骤 5。

### 做了什么

- 内核新增 `PreviewPump`（`core/preview/preview_pump.{h,cpp}`）：自有线程串行执行
  `IPreviewFrameSource::RenderFrame`，主线程只 `Request` + `Lock/blit/Unlock`。
- 新增 `IPreviewFrameSource` 接缝（`preview_frame_source.h`），`PreviewRenderer` 实现之
  —— 目的：泵能被注入**假帧源**做确定性并发测试（真实链路依赖 Metal + 解码，测不了并发语义）。
- `PreviewRenderer` 加 `Timings` 埋点（acquire / import / draw / total）。
- `gfx_device.cpp`：命令队列由「每帧 `CreateCommandQueue`」改为**按设备复用**；
  新增 `ICommandQueue::NativeHandle()` → `IGfxDevice::SharedQueueHandle()` →
  `cq_preview_shared_queue()`。UI 侧 blit **必须**用这条队列（跨队列 Metal 不保证顺序）。
- C ABI：`cq_preview_pump_*`（8 个）+ `cq_preview_shared_queue` + `cq_preview_last_timings`。
- Swift：`PreviewPump.swift`（新）、`Previewer.sharedQueueHandle` / `lastTimings`。
- SharedUI：`MetalPreviewView` 改成只 blit（连续/按需两种节奏 + 自驱追帧）；
  `PreviewFrameRenderer` 用共享队列；`AppEntry` 建泵，60Hz 取帧请求 / 30Hz 播放头发布。

### 实测（关键产出，已写进 baselines）

| 项 | 数字 |
|---|---:|
| 连续递进请求单帧 total（128x128，Release） | 99.3 ms（取帧 93.3 ms = **94%**） |
| 同上 Debug | 96.3 ms |
| App 侧 1s 播放（1280x720） | 请求 59 / 渲染 **14** / 合并 43（Release XCFramework；Debug 为 3） |
| Request 是否阻塞 | 否（单帧 50ms 时 10 次 Request 耗时 0ms） |

**帧率没有提高** —— 瓶颈是取帧策略：顺序播放每帧都 `kExact` seek = 每帧重解一个 GOP
（P38）。已开 `docs/tasks/TASK-MEDIA-021.md`，**故意**不在本次写集内改（它动的是
精确取帧的语义边界，要有专门的逐帧断言用例）。

### 踩的坑

- **P36**：消费端持锁期间调 `Request` → 死锁（同一把锁）。第一版单测直接挂死。
- **P37**：跨 MTLCommandQueue 无顺序保证 → 共享队列是刚需，不是优化。
- **P38**：顺序播放每帧 seek（见上）。
- 禁异常构建（Pods target 显式 -fno-exceptions）下 **`try` 都编译不过** ——
  `cannot use 'try' with exceptions disabled`。已去掉 try/catch，与 TaskRunner 同策略。

### 决策

ADR-0013（预览取帧的线程归属与共享命令队列）：泵放内核（不是 UI 层 GCD）——
理由：非 UI 逻辑（红线 #1）、三端不重写、可被 C++ 单测覆盖。
与 UIA-010 D2「时钟不跑线程」不冲突：泵是**可选组件**，UI 决定建不建。

## MEDIA-021：顺序取帧快路径（第二轮，约 17:30~20:00）

- **目标**：P38 修复——顺序播放不再每帧 seek 重解 GOP（HANDOFF-004 §5 第 1 优先级）。
- **写集**：`core/include/cq/media/system_frame_provider.h`、`pal/apple/media_decode.{h,mm}`、
  `tests/CMakeLists.txt`、新增 `tests/unit/test_media_sequential_acquire.cpp` +
  `test_media_sequential_real_apple.cpp`。文档：ADR-0014、TASK-MEDIA-021、
  media.md、pal-apple.md、baselines、pitfalls、HANDOFF-004。
- **结果**：
  - 顺序取帧 acquire 93.3ms → **4.45ms**（Release，GOP60/B帧3，120 帧顺序请求），
    14.8x vs「每帧 seek」对照；逐帧 pts 严格递增/区间归属/快慢一致 120/120。
  - 自适应阈值 `proven_span_`（实证学习，无拍脑袋常量）；`consumed_` 修复
    （同目标重复请求重新 seek，旧实现返回错帧）。
  - **意外收获**：逐帧 pts 断言暴露三个既有正确性 bug（慢路径同样中招）——
    P39 VT 完成序回调、P40 首帧时长兜底 pts 差（B 帧素材区间报宽 4 倍）、
    P41 Flush 后旧在途帧污染。全部修复；修复前 kExact 在 B 帧素材上系统性差帧。
- **验证**：Debug 42/42、Release 42/42、media_sequential_acquire 46 断言、
  media_sequential_real 7 断言、swift 23/23、SharedUI 20/20（XCFramework 重打包）。
- **坑**：测试请求网格必须整数 ticks（浮点 ms*120 截断污染断言与均值）；
  排障手法 = 三个独立诊断程序逐层剥离（裸 decoder 弹出链 → 慢路径复刻 →
  demux 独立验证），比在主链路里加打印干净。
- **剩余风险**：真机（iPhone 17 Pro）未验——顺序播放实际帧率、回退 seek
  正确性；`WaitForAsynchronousFrames` 全等流水线深度受限（ADR-0014 §后果 4）。

## P33：MediaImportTests flaky 根因定位与修复（第三轮，约 20:00~21:00）

- **触发**：HANDOFF-004 §5 第 3 优先级「probe 返回 0 时长，根因未证」。
- **根因链（三层叠加，全部实证）**：
  1. `loadValuesAsynchronouslyForKeys` 的 completion 只 signal 不查
     `statusOfValue`——终态含 Failed/Cancelled，失败时 `[asset duration]` invalid；
  2. invalid 经 demuxer `ToRational` 变 `{0,1}`，timescale=1 骗过 probe 检查
     → probe 以 kOk 返回 value=0（hypothesis 证实）；
  3. Swift importMedia 在 `value > 0` 处失败 → 素材库空 → 测试越界崩溃。
- **排障中的关键发现**：加载失败后重建 AVURLAsset，其 completion 可能**永不
  触发**（同 URL 进程级污染，实测 5s 无回调）——`DISPATCH_TIME_FOREVER` 无限
  等 = probe 挂死。首版修复被 testImportInvalid 抓到挂死（xctest 10 分钟无响应，
  sample 定位到 semaphore_wait_trap）。
- **修复**：终态检查 + 5s 有限超时 + 文件不存在 stat 跳过重试（13ms 返回）+
  probe 补 `value<=0` 防御。不存在文件 probe：挂死 → 13ms 诚实失败。
- **手法记录**：xctest 挂死 → `sample <pid>` 直接看主线程栈（两分钟定位到
  semaphore_wait_trap），比加日志/猜快得多。
- **验证**：Debug 门禁 42/42；SharedUI 全量 ×3 连续 **20/20 全绿**
  （4.2~6.1s 稳定，50% 失败未再复现）→ P33 verified。

## 第四轮（新会话，约 21:00 起）：P33 第二层根因 + UIA-011 letterbox/fit

### P33 复跑翻案 → 第二层根因（importMedia 版本差值竞态）

- 新会话复跑 SharedUI 全量 ×3：**6/3/0 失败** —— 上一轮「内核修复后 ×3 全绿、
  50% 失败未再复现」**不可复现**。失败签名仍是 importMedia 7000，但 probe
  分支修复后只会返回 2000 → 7000 另有来源。
- 给 importMedia 各失败分支加诊断（分支名 + 内核 raw 码 + 版本/耗时），
  一轮抓到现行：`track wait: version 0 -> 2, elapsed=10μs, tracks=1`。
- **根因**：importMedia 等 addTrack 落地的判据是「版本号 > versionAtStart」，
  但 **registerAsset 也 Publish 推版本**（editor_model_state.cpp:80）——版本
  差值无法区分是哪条命令落地。在途 registerAsset 先应用 → 等待提前通过 →
  查询还没有视频轨 → `videoTrack == nil` → 7000。负载越重窗口越大。
- **修复**：等待判据改为轮询目标效果本身（`queryTracks` 出现视频轨，10ms
  间隔 / 5s 上限；快照读纳秒级，轮询安全）。三个失败分支补正式日志。
- **验证**：SharedUI 全量 ×3 **20/20**（4.2~4.9s；修复前失败用例烧 5s 超时，
  套件 9.9~14.8s —— 时长回归正常也是旁证）。教训已并入 pitfalls P33：
  **flaky 的「N 次全绿」只是概率证据，必须配合失败签名闭环**。

### UIA-011：预览宽高比适配（letterbox/fit）——任务整体收口

- **决策**：ADR-0015。fit = 纯几何映射，三种模式都能用「视口矩形」一个原语
  表达 → 接缝选 **GFX/PAL 编码器 `SetViewport`（additive）**，不碰 IBlitPass
  与 MSL（保住 SharedUI 逐值锁定不变量），RT→drawable 恒等 blit 不动。
  备选（blit uniform / UI 层适配）及理由见 ADR。
- **实现**：PAL `ICommandEncoder::SetViewport`（像素、原点=target 左上、
  可大于目标、不调用=整目标）+ Metal `MTLViewport` 直映 + GFX 转发；
  `PreviewRenderer::FitMode`（stretch 默认/contain/cover，atomic setter，
  `ComputeFitViewport` 几何计算，源尺寸未知诚实退化 stretch）；C ABI
  `cq_preview_set_fit_mode`；Swift `Previewer.setFitMode(.contain/.cover/.stretch)`；
  SharedUI AppEntry 产品装配显式 contain。
- **实踩坑**：源尺寸必须在 `ReleaseFrame` **之前**捕获 —— lease 归约把
  frame 重置为 `MediaFrame{}`，首版在归还后读 width 得 0，fit 被退化成
  stretch（contain 像素断言抓到 → FIT-DBG 打印定位，10 分钟闭环）。
- **门禁**：Debug 42/42、Release 42/42；preview_renderer **51** 项
  （[8] contain bar 黑 + 内容真值 / cover 无 bar）、c_abi_preview **78** 项
  （set_fit_mode 契约）、gfx_device **30** 项（用例 C 视口内外像素断言）；
  XCFramework 三切片重建 + prepare 后 swift 23/23、SharedUI ×3 20/20。
- **文档**：ADR-0015、TASK-UIA-011、TASK-BACKLOG 登记、
  `.ai/modules/{preview,gfx}.md`、pitfalls P33、HANDOFF-004 §5。
- **性能**：fit 为每帧一次整数几何计算 + 一次视口设置，无可测量项，
  baselines 不新增（明确不适用）。
- **剩余**：真机（iPhone 17 Pro）验证 contain 观感（与 iOS 编译验证同一批）。
