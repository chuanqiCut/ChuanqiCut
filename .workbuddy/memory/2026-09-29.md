## 修复 XCFramework 打包失败（HANDOFF-002 遗留项）

接手后第一步先实测确认根因，不沿用上一轮的推测。结果：**旧推测（bitcode）是错的**。

**真因**：`cmake/CompileOptions.cmake` 的 `CMAKE_INTERPROCEDURAL_OPTIMIZATION_RELEASE=ON`。
Release + LTO 时 clang 产出 bitcode-only `.o`（magic `0x0b17c0de` + `BC\xc0\xde`），
不是 Mach-O，`xcodebuild -create-xcframework` 报 "Unknown header: 0xb17c0de"。
与 ENABLE_BITCODE 无关，当初据此加 `-fno-embed-bitcode` 方向就错了。

**第二个坑**：原写法 `set(... CACHE BOOL ... FORCE)` —— FORCE 让命令行
`-D...IPO_RELEASE=OFF` **静默失效**。第一次修复传了 OFF 却完全没生效，是靠
「产物字节数与修改前完全一致」察觉的。改成项目显式 option `CQ_ENABLE_LTO_RELEASE`。

**顺带发现的严重缺陷**：`.gitignore` 里有裸 `build/` 规则（任意层级匹配），
把 `tools/build/` 一并忽略 → **三个构建脚本自建库以来从未入库**，而交接文档 §5
还在教人去跑它们。这类误忽略是静默的，`git status` 干净但 clone 出来跑不了。
已改为只保留锚定的 `/build/`，并补了 `tools/build/` 入库 + clone 自举验证。

**新增两道门禁**（基于「绿灯 ≠ 可用」的教训）：
- 合并前 `otool -l` 断言切片不含 bitcode
- 合并后消费者侧真实链接并运行 macOS 切片（`tools/build/smoke_link.cpp`）

**验证**：三切片 `.o` 头部 `dec0170b` → `cffaedfe`；xcframework 三切片生成；
真链运行输出 `StatusToString(kOk) = OK`；主构建 Release LTO 未退化；
CTest Debug/Release 均 22/22；PAL 门禁 0 violation；golden 21/21；selfcheck 18/18。

commit：`762b690`、`6d2d19f`

## CORE-008 线程模型与队列骨架（同日完成）

ARCH-001 §6 此前**只是一张 ASCII 图**：7 类线程角色定义好了，Session Thread 不存在，
"主线程零阻塞"无从执行也无从验证。CORE-005 的 concurrency.h 已声明
「线程池属 CORE-008，不在 base 层」，本次接住，未重复发明原语。

- `thread_model.h`：ThreadRole + thread_local 角色标记。默认 `kUnknown`，
  **不把未标记线程猜成 main**（误判会让零阻塞守卫生效不了）
- `task_runner.h`：TaskRunner 串行执行器。`Post()` 非阻塞，满则
  `kResourceExhausted`；**刻意不提供 PostAndWait**——那会让铁律在 API 面被破坏得更隐蔽。
  复用 CORE-005 的 BoundedQueue + CancelToken。任务内禁抛异常，且刻意不 try/catch
  （捕获等于默许异常流向内核）。析构无条件 RequestCancel + join。

**验收「主线程零阻塞可测」**：投递含 100ms sleep 的任务，`Post()` 实测 **0.030ms**
（16ms 预算的 1/533）。CTest 24 → **25**（Debug + Release 都过）。

## CORE-009 EditorSession 门面（同日完成，依赖链打通）

ARCH-001 §4.1 定义 session = 「对外唯一门面」，它是 BIND-001 要冻结成 C ABI 的对象，
此前完全不存在 —— 是 `BIND-001 → BIND-002 → 所有 UIA-*` 依赖链的最后缺口。

- `editor_session.h`：Submit（异步不阻塞）/ CurrentSnapshot / ChangesSince / 观察者
- `snapshot.h`：Snapshot{version,digest} + ChangeRecord + **ISessionState 扩展点**

关键约定：
- 版本号**只在变更成功时递增**；失败/取消不推进（UI 会错刷）
- 观察者在 **session 线程**回调 → Swift 侧必须自己 dispatch 到主线程
- **不越界**：不做 TimelineModel（MODEL-001）、不做 Command/Undo-Redo（MODEL-002）。
  用 ISessionState 扩展点 + 测试实现把机制跑通，避免门面变成第三个断接口

**踩到的坑**：`Config cfg = {}` 作为默认参数 → clang 报
"default member initializer needed within definition of enclosing class"（嵌套类的
默认成员初始化器不能在类外默认参数里用）。改为两个构造重载 + 委托构造。
另：测试里 lambda `[&]` 捕获循环变量 i 的引用，所有任务读到 i==8，
FIFO 断言莫名其妙失败 —— 改 `[&, i]` 按值捕获。

验证：CTest 25 → **26**（Debug + Release）；Submit 实测 0.005~0.010ms；
三切片 + 链接冒烟；门禁 21 头 0 violation。

## BIND-001：cq_sdk.h 纯 C ABI 冻结（同日完成）

此前是 INFRA-001 占位（只有 typedef），nm 可见全是 C++ mangled 符号，
Swift/Kotlin 完全接不上。现在门面有了，冻结才有支撑。

冻结内容：版本（CMake 注入，不硬编码）+ 状态码（复用内核数值，不复制枚举）
+ `cq_mark_main_thread()`（CORE-008 守卫入口）+ `cq_query_capability()`（红线 #3 入口）
+ CQSession 会话门面。回调一律「函数指针 + void*」（std::function 跨不了 C ABI）。

**零 C++ 类型靠机器校验**：`tests/unit/test_c_abi.c` 是真正的 C TU。
已反向验证：往头文件插入 std::string → C TU 立即 fatal error。

又踩到同类静默缺口（**第三次**，记为 pitfalls **P4**）：根 CMakeLists 只写
`LANGUAGES CXX` → CMake **静默不编译 .c**，只在链接期报"缺 main"。
判据不是"没报错"，而是**构建日志里有没有 `Building C object` 这一行**。

踩到的另两个坑：
- `struct CQSession` 定义在匿名 namespace → 与头文件 typedef 命名歧义，移到全局
- `new` 会抛 bad_alloc，与"内核禁异常"冲突 → 用 `new (std::nothrow)`

验证：CTest 26 → **27**（Debug + Release）；三切片 + 链接冒烟；门禁 21 头 0 violation。
