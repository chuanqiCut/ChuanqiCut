# ADR-0014：顺序取帧快路径与解码器显示序重排

- 状态：已接受（2026-10-04，TASK-MEDIA-021 落地）
- 关联：`ADR-0013`（预览取帧线程归属，其 §后果 2 条明示本问题）、`TASK-MEDIA-021`、
  `TASK-UIA-010`（子步骤 5 实测引出）、pitfalls P38/P39/P40/P41
- 影响面：`core/include/cq/media/system_frame_provider.h`（编排层）、
  `pal/apple/media_decode.{h,mm}`（PALA-011）、`tests/unit/test_media_sequential_*`

## 背景

UIA-010 子步骤 5 的埋点实测（`baselines.md`）：顺序播放时单帧 acquire 93.3ms
（Release，GOP60 素材），占单帧总耗时 94%；上限帧率 ≈10fps。根因
（P38）：`SystemFrameProvider::AcquireFrame` 只要目标时间变化就
`Seek()`（demuxer seek + decoder Flush），随后从关键帧重解整个 GOP——
顺序播放每帧都付一遍 GOP 代价。孤立请求同一素材仅 ~5ms，证明成本全在策略。

## 决定

### D1：顺序前进的 kExact 请求跳过 seek（快路径）

`TrySequentialAcquire`：上次交付帧区间终点 ≤ t、且跨度 ≤ `proven_span_` 时，
从当前解码位置继续 `AcquireExact`，不 seek。kExact 的「展示区间归属」语义
不变——拿到的仍是包含 t 的那一帧。

**阈值不拍脑袋**（E6 教训）：`proven_span_` =「已证实的无关键帧最大跨度」，
数据只来自两处实证——连续两个关键帧的间隔（Feed 序列全程观察）、关键帧到
交付帧的距离。初始 0（全走慢路径），错了最坏多解一个 GOP（与旧行为同阶），
不会爆炸。正确性依据：区间内无关键帧时，seek 只能落到区间之前的关键帧，
继续解码的距离严格不大于 seek 的解码距离。

### D2：回退与学习期照旧 seek，且 seek 后同目标重复请求必须重新 seek

- 回退（t < 上次交付）：解码器已越过目标，只能 seek（快路径拒绝）。
- 快路径无法交付「上次交付过的同一帧」（lease 语义下像素已让渡调用方）；
  重复/微进请求走慢路径重解。
- **consumed_ 语义（修复的既有 bug）**：`seek_target_` 被一次取帧消费后，
  重复同目标请求必须重新 seek——否则 AcquireExact 的「越过兜底」会返回
  **下一帧**（违反 kExact）。旧实现在此返回错帧。

### D3：解码接缝的「先喂后弹」循环结构（编排层硬约束）

`AcquireExact` / `AcquireKeyframeBefore` / `AcquireNearest` 统一改为
**每轮先 ReadPacket+Feed 一包，再连续 PopFrame**。原因见 P39：平台解码器按
完成序回调，B 帧在其参考帧之后完成；若「弹不出才喂」，队首 P 在 B 尚未喂入
时就弹出，任何重排判据都无信息可用。预喂让每个 B 的存在在其前驱弹出前被
decoder 的重排判据看见；异步管线中预喂帧的解码与等待重叠，增量成本 ≈ 一次
demux ReadPacket。

### D4：PALA-011 按「显示序连续性」重排弹出

VT 输出回调按**完成序**（≈dts 序），不是显示序（P40：实测 145/300 非单调）。
`PopFrame` 重排判据，**不需要知道 B 帧深度**：

> 队列最小 pts 帧可弹，当且仅当 `pts == 上一弹出帧 pts + 其 duration`
> （duration 即相邻 pts 差，CFR/VFR 皆成立）。不匹配 ⇒ 显示序下一帧尚未
> 入队：在途帧（pending 非空）可能补上 → 等待；无在途帧 → 返回 kIoNotFound，
> 由 provider 继续 Feed（「B 未喂入」正是靠这个揭示的）。

配套修复（同族，均由逐帧 pts 断言暴露）：

1. **首帧时长兜底改用 dts 差**（P41）：B 帧文件前两个喂入包的 pts 差 =
   (bframes+1) 帧（本 golden = 4 帧），曾致首帧展示区间报宽 4 倍、
   kExact 在关键帧提前命中（画面差帧）。CFR 下 dts 间隔恒为一帧。
2. **Flush 先 `WaitForAsynchronousFrames` 再清队**（P41 同族）：在途回调
   可能在 Flush 后才到达，不清会把上一解码区间的旧帧漏进新序列首弹
   （实测 Seek(124000) 弹出旧 GOP 的 128000）。
3. **失败/取消后失效增量锚点**：Acquire* 半途失败时 decoder 相对锚点已
   漂移，锚点失效，下次走慢路径重新对齐。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 固定 seek 阈值常量（如「前进 <N 帧不 seek」） | N 无实测依据（E6 同族）；GOP 长度随素材变化，常量必然错 |
| decoder 内按 pts 全排序缓冲 | 需要「不会再有更小 pts 到达」的判据，B 未喂入时不存在 |
| 解析 SPS `max_num_reorder_frames` | 工作量大（VUI bit reader）；D4 判据无需该信息且对 VFR 成立 |
| provider 缓存确认帧再交付 | 违反解码接缝 lease 约定（decoder 同一时刻只持有一个可消费帧） |
| 候选帧延迟确认（弹出候选后继续解码验证） | 确认帧被丢弃，下一请求仍需重解；lease 模型下持有两帧即 use-after-free |

## 后果与已知限制

1. **实测**（Intel Mac，1080p GOP60/B帧3，120 帧顺序请求）：快路径 acquire
   均值 **4.45ms**（Release）vs 每帧 seek 对照 65.87ms（**14.8x**）；
   逐帧 pts 严格递增 120/120、区间归属 120/120、与对照逐帧一致。
   完整表见 `.ai/memory/baselines.md`。
2. 快路径命中条件依赖 `proven_span_` 学习（首 GOP 走慢路径，属预期）。
3. 流尾丢帧（demux 尽后仍缺显示序帧）时 drain 分支交付 `before`（t 前最近
   帧），区间归属轻微失真——流本身已损坏，可接受；会话不挂死。
4. `PendingMinPts` 式等待用 `VTDecompressionSessionWaitForAsynchronousFrames`
   （等全部在途帧），流水线深度受此限制；后续可用 per-frame 同步优化。
5. 快路径无 seek 的前提下 demuxer reader 连续读——不再每帧重建
   AVAssetReader（顺带消除了一个 reader 状态异常源）。
