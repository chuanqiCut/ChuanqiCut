## bug 1 — setpts 缺 `/TB` + timebase 量化（导致 VFR 样本退化成 CFR）

`setpts` 返回值单位是 **timebase units 不是秒**，漏 `/TB` → pts 全塌为 0 → CFR。
更隐蔽的第二层：**`-enc_time_base` / `settb` 都改不了 setpts 运行时的 TB**（二者只作用于 encoder 及后续），
setpts 仍跑在输入时基 1/fps 上，**任何小于 1/fps 的间隔必然被量化抹平**。
→ 结论：别试图用表达式表达 0.02s 这类亚帧间隔，改为**把排布落在整数 tick 上**：

```
setpts=(N+floor(N/2))*(1/30)/TB      # 间隔严格交替 1 tick(30fps) / 2 ticks(15fps)
```
实测：`帧数=90 distinct间隔=3 {0.03333:46, 0.06667:42, 0.1:1}`，这是录屏/网络流最典型的真实 VFR 形态。
另需同用 `-fps_mode vfr`，缺则 ffmpeg 会把不均匀时间戳重采样回 CFR。

**附带结论：VFR 样本的 duration_s ≠ frame_count/fps**（90 帧 @30fps 名义 3.0s、实际 4.4667s），
这是 VFR 的固有属性。已把 manifest 的 `duration_s` 改成**实测值**并加注释禁止按 3.0 回填。

## bug 2 — rotation 只能通过 `-display_rotation` 作为 **INPUT option** 写入

六种写法实测（**字节级解析 tkhd 变换矩阵**，不依赖 ffprobe 是否选择显示某字段）：

| 写法 | tkhd 结果 |
|---|---|
| `-metadata:s:v rotate=90`（重编码 / `-c copy`） | 单位矩阵 ❌ |
| `-display_rotation` 作 output option | ffmpeg 报错拒绝 ❌ |
| mkv 中转保留 tag 再 remux | 单位矩阵 ❌ |
| **`-display_rotation:v:0 90 -i X -c copy`** | **a=0 b=-1 → -90° ✅ 唯一可行** |

**根因认知**：mp4 里旋转的正确载体是 **tkhd display matrix**，`tags.rotate` 是 ffmpeg 6 已废弃的遗留写法 ——
生成器就算写了 `-metadata rotate=90`，muxer 也不会落成 tag。
→ **该改的是校验侧**：`verify.py` 新增 `_mp4_display_rotation()` 读 tkhd 矩阵。
这**不是放宽校验而是收紧** —— 原来只要有个 tag 就过，现在必须字节级证明矩阵真的存在。
验证：独立脚本（不复用我改的函数）读出 `-90°`，对照无旋转文件是 `0°`。

`src, v = _ffmpeg_common_video_args(spec)` 里 `v` 装着 gop_size / bframes / pix_fmt / preset，

我独立验算确认：**八种帧率里只有 23.976 在 60000 下不精确**，其余七种全整数：

```
23.976 = 24000/1001 → @60000 = 2502.5 ❌  | @120000 = 5005 ✅
29.97  = 30000/1001 → @60000 = 2002   ✅  | @120000 = 4004 ✅
59.94  = 60000/1001 → @60000 = 1001   ✅  | @120000 = 2002 ✅
```

注意 worker 的「八帧率零漂移」是在**各自原生 timescale** 下测的（23.976 用 ts=24000，
29.97 用 ts=30000），**不是**在统一 60000 网格下 —— 它没有偷偷用 60000 凑数，
而是单独加了一条测试 `TestTimescale60000InsufficientFor23_976` 固化该事实。这个处理是对的。

三个选项（**未拍板，worker 严守任务卡「不许就地改数字」**）：
- **A（worker 建议，我倾向）**：ADR-0006 改 `60000 → 120000`（= lcm(60000, 24000)）。
  验算 120000 对 NTSC 全家（15000/24000/30000/60000/120000 分子）都整数化，一劳永逸。
  代价：改 ADR 需评审；int64 上限减半但仍约 240 万年。**现在改成本最低**（只有 CORE-001/002 用到该常量）。
- **B**：保持 60000，接受 23.976 素材进项目时间轴时显式舍入（当前实现已支持任意 timescale + 显式舍入方向）。
- **C**：不设单一项目 timescale，各素材带自己的 timescale（当前实现已支持），转换时显式舍入。

120000 验算依据：120000/15000=8、/24000=5、/30000=4、/60000=2、/120000=1，全部整除。

### P0-2 澄清：他说的不是「规避 LGPL」，是「排除 GPL、保持 LGPL」

原话"FFmpeg 理论上可以先不使用 lgpl 相关的代码" —— 我第一遍**误读**成"规避 LGPL"，
并据此在 ADR-0010 初稿写了"传哲判断有误"。**那是我的误读，不是他的错误**（已更正）。

他随后澄清：「先不使用 **GPL** 相关的代码，**保持 LGPL** 的能用」。

**这与已构建产物完全一致，无需任何改动**：
`license=LGPL-2.1-or-later`、`CONFIG_GPL=0`（无 GPL 代码）、`CONFIG_LGPLV3=0`、

**但有一条他要留意（已写进 ADR-0010）：LGPL ≠ 无义务。**
LGPL v2.1 对静态链接的核心要求是「接收者能用修改过的库版本替换并重新链接」。
