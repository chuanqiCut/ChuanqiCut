## 0. 一句话结论

**文档没有系统性说谎，但它回答的是另一个问题。**

上一轮的产品命题是「界面丑 + 播放卡」，所以 RESEARCH-008 白纸黑字把「不复刻对标 App的内容能力」写进了 §5 非目标。任务卡（UIA-034~038）忠实地执行了这个范围：全是容器、播放头、手势、工具栏这类**骨架与交互**。它们都"真的完成了"。

问题是：**目标没有随阶段升级**。当期望从"像对标 App"变成"能像对标 App那样剪完一条片子"时，那张 22 项对照表里 15 项红色的空缺就暴露了。

真正的硬伤只有一条，但它是致命的：**没有任何导出路径**。一个不能出片的剪辑软件，其余功能做得再好也只是 Demo。

### 3.3 制度性根因（比个别错误更要命）

`AGENTS.md` 的「验证」节定义：**完成 = 门禁通过**。而门禁构成是 `build_core.sh`（编译）+ `ctest`（单测）+ golden 齐备性。

**这条口径里没有"用户可见功能是否可用"这一栏。** 于是 `enabled:false` 的按钮、没接出来的 C ABI、缺失的导出，全都不会让门禁变红。系统性地产出"绿而空"是正常的，不是某个人失职。

**建议在 AGENTS.md「验证」节补一句硬规则**（这条本期就要改，否则新增功能照样出现"绿而空"）：

> 新增交互式功能的验收必须给出「用户操作路径 → 可观察结果」的走查证据（截图或日志），  
> 仅编译绿 + 单测绿不足以标记完成；按钮/入口若为占位，必须在任务卡写入"占位"并在验收表列出。

## 4. 对标 App功能优先级判定

不看更牛的软件（Final Cut / Premiere / DaVinci），只锚定**对标 App移动端**的日常操作。

对标 App用户一条典型视频用到的操作覆盖面 `hypothesis`（**未做用户调研，未经数据验证，仅作为排期假设**）：

| 优先级        | 功能                            | 理由                        |
| ---------- | ----------------------------- | ------------------------- |
| **P0 生命线** | 导出成片、**分割**、删除片段、多级撤销         | 不能导出=玩具；不能分割=不能剪辑。这三条缺一不可 |
| **P0 配齐**  | 背景音乐 / 音量 / 关闭原声、添加文字、比例与画布背景 | 手机端对标 App的"标配三件套"             |
| **P1 对标 App味** | 变速、转场、滤镜、参数调节、淡入淡出、画中画/多轨     | 决定了"像不像对标 App"的观感             |
| **P2 进阶**  | 关键帧动画、蒙版、混合模式、抠像、ASR 字幕、曲线变速  | 可以放到已经能出片之后               |
| **不建议做**   | 素材商城、模板、云剪、多端协作               | 是产品运营不是剪辑能力，且有商业模式依赖      |

**关键判断**：P0 里的**分割、删除、导出、音量/BGM** 全部**不依赖 RenderGraph 和效果管线**。  
而 P1 的滤镜/调色/转场**必须等** `RENDER-001`（RenderGraph）+ `MODEL-003`（属性系统）+ Portable shader 层。

~~这就是排期的抓手：先把不需要地基的功能全做完，地基当并行线。~~  
**此判断已于 2026-10-10 21:47 被传哲否決并撤回**（ADR-0034）：不得为赶产出绕开地基。

## 5. 对齐路线：地基先行，分批推进

> 依据 **ADR-0034**：禁临时方案、分批闭环、写集不相交的批次可并行。
> 每条 CMD 都有独立出口标准，交付后按 `docs/reviews/TEMPLATE-真机问卷.md` 出问卷。
> 本章内容已于 2026-10-10 21:47 重排（原「Wave 1 导出优先」方案已被传哲否決）。

### 5.1 为什么必须地基先行（这是重排的唯一理由）

架构红线 #9 要求「**预览与导出走同一张 RenderGraph**，只换输出目标与时钟源」。
当前没有 RenderGraph —— `engine/core/CMakeLists.txt:53-55` 明确写着「本期不做 RenderGraph」，
预览走的是单 blit pass（`preview/preview_renderer.cpp:108` `RenderFrame`）。

若按原计划把导出直接接到现有预览渲染器上，就会形成**预览与导出两条不同的渲染路径**。
这不是省事，是把 ADR-0014 的坑再踩一遍：本仓已因为「相机滤镜 vs 编辑器特效两套实现」
背过一次债（`TASK-BACKLOG.md:414-415` 有案底）。日后要把已完成的多轨/文字/贴纸/滤镜
重构成 Graph 节点，成本随每批功能线性增长。

**结论：RenderGraph（RENDER-001）+ 属性系统（MODEL-003）+ Portable shader（SHADER-001）
不是优化项，是第一批就必须立的地基。** 依赖它的功能排队等待，不在上层写绕过实现。

代价要写清楚：**用户可见的第一个出口（导出成片）被推后**，这是 ADR-0034 明确接受的代价。

## 6. Mac 与 iOS 分端形态

> 依据 ADR-0034 §6：**不再把一套 iOS 视图塞进 Mac 窗口**，两端按各自特性各自设计。
> 据此，**原 W1-5「给 Mac 补一个底部工具栏」的补丁方案予以撤回** —— 那仍是套壳思维。

### 6.1 iOS：移动端编辑范式

沿用已落地的 UIA-034~038 UIKit 三区结构，形态已定型：

- 预览（点击播放/暂停，播放时浮层控件）→ 时间线（手势优先）→ 底部工具栏（单焦点 + 抽屉）
- 选中片段后底栏整体替换为二级操作（分割 / 删除 / 复制 / 音量 / 变速）
- 双指捏合缩放时间线、长按拖拽、右缘裁剪
- 竖屏单手操作优先；键盘不作为主要输入

尚未完成：一级工具栏的**音频 / 文字 / 特效三项目前是 `enabled:false` 空闭包**。
按 ADR-0034 §2 这属于占位，须在对应能力落地时真实启用，或显式列入「本期不做」。

### 6.2 macOS：桌面专业范式（需先出形态稿）

现状是 macOS 主窗口直接挂 iOS 那套 `EditorView()`，且其 `macLayout` 连底部工具栏都不渲染，
导致 Mac 端可见能力**少于** iOS。正确做法不是补按钮，而是按桌面形态重做：

| 维度 | macOS 目标形态 |
|---|---|
| 布局 | 三栏：左素材库 / 中预览 / **右侧常驻属性面板**（对标对标 App专业版） |
| 菜单 | 菜单栏命令体系：建 File / Edit / Clip 三组（当前全仓零 `CommandMenu`） |
| 工具栏 | 顶部工具栏（非底部），与菜单同源的操作集合 |
| 多窗口 | 预览可独立浮窗；允许多项目窗口并存 |
| 输入 | 键盘快捷键全表（已有 Cmd+Z / Cmd+Shift+Z，需扩充并成文）、右键菜单、滚轮缩放时间线 |
| 导入 | Finder 拖拽到时间线 / 素材库（当前只有 `fileImporter` 单选） |
| 分栏 | `HSplitView` 宽度持久化 |

**新卡建议**：`UIA-039` macOS 编辑页桌面形态（需要先出形态稿，再拆子卡）。

### 6.3 两端共享什么

只共享 **EditorViewModel 与内核 Command 链路**（ARCH-005：共享的是状态与命令，不是 UI 框架）。
UI 布局、交互、菜单、快捷键**一律不共享**，各自独立演进。

## 7. 已裁定的决策（备查，勿再议）

> 以下两项在初稿中是「待拍板」，传哲 2026-10-10 21:45 一并裁定，此处留档便于复盘。

### 决策 A：效果地基何时建 —— **裁定：地基先行，依赖它的功能排队等待**

原计划把地基当并行线、先把不依赖它的功能做完。**已否決。**
理由：那样会让导出绕过 RenderGraph，预览与导出出现两条渲染路径，违反红线 #9，
且后续多轨 / 文字 / 滤镜全部要返工。详见 §5.1。

限定：地基只做**最小可用 RenderGraph**（单一 pass 链 + 参数挂载够用即可），不追求完整节点图。

### 决策 B：文字/贴纸渲染放内核还是先 Swift 侧 —— **裁定：否決临时实现，走内核**

原倾向选项 B1（文字先在 Swift 侧用 Core Text 做，标注临时实现后替换）。**已否決。**

传哲原话：「**不搞临时方案**」。这是 ADR-0034 §3 的直接应用：
本仓已经因为「相机滤镜 vs 编辑器特效两套实现」背过一次技术债（ADR-0014 的代价），
不允许在同一个产品里第二次出现两套渲染路径。

因此：

- 文字（`EDIT-004`）/ 贴纸（`EDIT-005`）排在 **B6**，依赖 B0 建立的 RenderGraph + Portable shader；
- 不接受任何「先用 Swift / AVFoundation / CoreImage 顶着」的实现；
- 由此造成的可见产出后移，是**已被接受的代价**，不作为回退本条的理由。

## 8. 风险与明确不做

| 风险 | 处置 |
|---|---|
| B4 批次会改动 `cq_sdk.h`（热点文件 / ABI 变更） | **必须走集成机**，且需连带更新 `tools/docs/gen_api_reference.py` 生成的 `docs/api/engine-api.md`（`--check` 会拦） |
| Platform 层导出缺进度回调，只有 `FrameCount()` 可轮询 | B4 的进度验收写「轮询式进度」，先不承诺亚秒级精确 |
| Apple muxer 硬编码 MP4、码率只有档位 | B4 不承诺容器 / 码率自定义；写进「本期不支持」清单 |
| `RENDER-001` 需反转 `engine/core/CMakeLists.txt:53-55` 的「本期不做 RenderGraph」 | 属架构反转，**需先立 ADR**（不能只在 Research 里写一句），并联动 COLOR-001 / EXPORT-002 |
| Portable shader 的 SPIR-V 生成链从未跑通（`blit_fullscreen_msl.h:4-7` 自陈未落地） | B0 开工前先做一个**极窄 spike** 验通「glsl → SPIR-V → MSL」最小链路，避免整批卡死 |
| 四个 Platform 工厂（`audio` / `inference` / `net` / `fs`）长期只有声明无实现 | B2 开工前逐个确认归属；`audio` 由 B2 承接，其余三条登记进 TODO-POOL |
| **当前工作区有未提交改动**（含 `AGENTS.md`、`project.yml`、`Podfile`、`Podfile.lock` 等热点文件） | **B0 / B1 开工前必须先决断这批改动**：提交、回退或确认无关。否则首批写集必然冲突 |
| `AGENTS.md` 处于 Modified 状态 | 它是生成文件，应由 `tools/ai/sync_context.py` 重生成，不应手改 |

**明确不做**（对齐对标 App范围内）：素材商城、模板、云空间、多端协作、社区分享。
**不做更牛软件的功能**：多机位剪辑、嵌套 / 复合时间线、XML/AAF 交换、专业示波器、节点式调色。
