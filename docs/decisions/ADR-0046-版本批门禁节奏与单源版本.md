# ADR-0046：版本批门禁节奏（显式小版本号）+ 单源版本 + ctest 按配置分档

- **状态**：已接受（2026-10-17，**传哲拍板**：门禁按「一个小版本」统一跑，不允许"写个小功能就跑一趟全量"；
  批次口径选定「引入显式小版本号 v0.x.y」；真机与问卷节奏**本轮不动**）
- **日期**：2026-10-17
- **决策者**：传哲（口径）+ 集成机（落地与取证）
- **依据**：[ADR-0030](ADR-0030-模块册分册制与阶段批门禁节奏.md) §4（本 ADR **修订其「阶段批」定义**，
  其余四条不动）、[ADR-0029](ADR-0029-双机分工与门禁跑批节奏.md)（双机分工）、
  `docs/reports/VERSIONS.md`（版本真源与批账）、`.ai/memory/baselines.md`「并行化后全量门禁第二趟」
  （52 用例逐个秒数）、pitfalls **P166 / P170 / P171**
- **影响面**：`VERSION`（新）、`docs/reports/VERSIONS.md`（新）、根 `CMakeLists.txt`（版本改从 `VERSION` 读）、
  `tools/ci/run_gate.sh`、`tools/ci/gate_scope.sh`（新）、`tools/build/build_core.sh`、
  `tests/CMakeLists.txt`（加 LABELS）、`.github/workflows/ci.yml`、真源 §验证 / §双机分工、
  [.ai/modules/core.md](../../.ai/modules/core.md)（基建卡归口，本仓无 `infra.md`，见 P174）
  —— **零业务代码改动**，红线 #1~#10 不触碰

## 背景

ADR-0030 §4 早就写了「开发期只做模块级自查，全量按阶段批」，传哲当时的原话就是要降低频率
（「开发中的门禁和真机测试不要那么频繁，阶段性去跑」）。但它是**纪律不是工具**，落地后暴露三个洞：

1. **"阶段"在机器上没有任何定义**。版本号分散在四类文件里各写各的：8 份 `*.podspec` = `0.1.0`
   （`ChuanqiCutFFmpeg.podspec` = `9.0.2`，那是 FFmpeg 上游 pin 的版本，不是产品版本）、
   两端 `Info.plist` 的 `CFBundleShortVersionString` = **`1.0`**、两端 `project.pbxproj` 的
   `MARKETING_VERSION` = `0.1.0`、根 `CMakeLists.txt` 的 `project(ChuanqiCut VERSION 0.1.0)`。
   → **没有一个被指定为真源**，且 `Info.plist` 与 `pbxproj` 在同一个工程里直接冲突
   （`MARKETING_VERSION` 存在时，构建期生成的是 `Generated Info.plist`，源码里那份 `1.0` 是死值、
   只在 Xcode 界面上骗人）。所以"到一个小版本了"这句话无法被判定，也就无法触发任何东西。
   > **订正（2026-10-17，同批）**：本 ADR 初稿写的是「`Info.plist` 写 `1.0`、**CMake `project()` 不带版本**」，
   > 后半句是错的——`CMakeLists.txt:10-11` 一直带 `VERSION 0.1.0`。错因是我只核了 podspec/plist/pbxproj
   > 三处就外推了第四处，没读根 CMakeLists。事实已按上面重写；
   > 本批的处置也随之改变：**不是"给 CMake 补版本"，而是"让 CMake 从 `VERSION` 读"**，
   > 使「CMake 侧版本 == `VERSION`」成为可机检判据。
2. **agent 跑全量是因为不知道该跑什么**。门禁有 18 步、跨 4 套配置树、6 个 SPM 包 + 2 个 Pod，
   而"改了 X 该验 Y"只存在于老手的脑子里。没有路由，保守的人就全跑 —— 一次 7 分钟，一天十几次。
3. **贵的和便宜的挤在同一档**。实测（2026-10-17 全量趟）52 个用例的分布**极端头部化**：

   | 分组 | Debug 秒数 | 占 Debug ctest |
   |---|---|---|
   | `media_sequential_real` 一例 | **58.23s** | **54.1%** |
   | 前 11 例（媒体/硬件/渲染链路） | **101.79s** | **94.6%** |
   | 其余 41 例 | **3.32s** | 3.1%（25 例 ≤0.05s） |

   而 **Debug 与 Release 跑的是完全同一套 52 例（交集 52/52，零差异）** → 244s 的 ctest 段里，
   绝大部分是"同一批硬件链路断言在两个配置各付一遍"。

## 决定

### 1. 版本批 = 全量门禁的唯一节奏单位；`VERSION` 是版本号的唯一真源

- 仓库根 `VERSION`（当前 `0.1.0`）= **唯一真源**；`tools/ci/run_gate.sh` 读它，把版本写进
  `gate-history.tsv` 的 `version` 列与 `gate-summary.md` 头部。
- 语义与升降规矩表在 `docs/reports/VERSIONS.md` §一。**升 `MINOR` 必须附一趟全量数字；窄检永不升号。**
- `VERSION` 放根目录**不违反 ADR-0019 §2**：那条禁的是"内容文档"，`VERSION` 与 `.clang-format`、
  `CMakeLists.txt` 同属基建文件。批次账（内容文档）落 `docs/reports/`（append-only 域）。
- 现存不一致中，**根 `CMakeLists.txt` 本批起改为 `file(STRINGS …/VERSION)` 读真源**（它原来硬编码
  `0.1.0`，正好与 `VERSION` 同值，所以这一改是"消除未来漂移"而不是修 bug）；
  **`Info.plist` 的 `1.0` 登记为待办**，本批不动 podspec / pbxproj（见 §明确不做）。

### 2. 门禁分四层，只有 L3 是全量；开发会话禁止跑 L3

| 层 | 谁跑 | 内容 | 实测成本 |
|---|---|---|---|
| **L0 编辑循环** | 改代码的人，每次改 | 单目标 `cmake --build --target <test 目标>` + `ctest -R <case>` | 秒级 |
| **L1 单卡自查** | 每张卡闭环前 | `gate_scope.sh` 路由出来的窄检命令；内核改动 = `core-dbg --skip-label heavy`（**≈15s**，见决定 3） | ≈15s~1min |
| **L2 合并快检** | 集成机每次拉远端 | `build_core.sh` + 相关包 `swift test` + **双壳真编译** + 冲突标记/旧号扫描 | ≈2~5min |
| **L3 版本批** | 只有集成机，**一个版本号一趟** | `run_gate.sh` 全量 18 步（含 `core-rel` **全 52 例**）→ 绿了才升 `MINOR` | 实测 427s（暖） |

**开发会话「跑全量」这件事本身是违规的**——不是"可以但别频繁"。理由：验收口径本来就归集成机
（ADR-0029/0030），开发机跑出的全量数字既不能当验收、又每次烧 7 分钟。

### 3. ctest 按配置分档：重例只在 Release 跑，Debug 只跑纯 CPU 例

- `tests/CMakeLists.txt` 给**语义上**依赖真实素材或硬件链路（VideoToolbox / AVFoundation / Metal）
  的 14 个用例打 `LABELS "heavy"`（逐个列在卡里）。
- `build_core.sh` 新增 `--skip-label <名>` → 透传 `ctest -LE`。
- `run_gate.sh`：**core-dbg 带 `--skip-label heavy`**（107.55s → 实测见 baselines），**core-rel 不带**（仍全 52 例）。
- ⚠️ **CI 的 Debug 步与本机**故意不同口径**（落地时改判，原写"同口径"）**：CI **保持全 52 例**。
  分档的目的是省**本机墙钟**（传哲这台机器上的 7 分钟），而 CI 的墙钟不花本机时间，
  跟着跳过只是少验。CI 因此成为 heavy 用例在 **Debug 档的唯一覆盖点**，也就是本节
  「代价 ①」的缓解措施本身 —— 把它改成"同口径"等于把缓解删掉。
  两边都打印名单（`ctest -N -L heavy`），跳过不打印 = 覆盖面缩了没人知道（P145/P170 同族）。
- **分档判据是语义的、不是秒数的**：不打"跑得慢"的标，打"需要外部条件（素材文件、硬件 codec、Metal）"的标。
  按秒数分档会在换机器那天静默变味（P171：同一用例两趟差 2×）。
- **为什么是 Release 而不是 Debug**：出货产物就是 Release（`build_core_apple.sh --config=Release`
  出的 xcframework），硬件链路本来就该在出货配置里验；而 Debug 保留的 38 例是
  time/status/command/model/abi/泵 这些**配置敏感**的纯 CPU 断言，双档都便宜，留着双跑不亏。
- ⚠️ **Debug 不是"带断言的那一档"**：本仓 `build_core.sh` 的配置行只有 `-DCMAKE_BUILD_TYPE`
  （**没开 ASan/UBSan**），且引擎里 `assert(`/`CQ_ASSERT`/`CQ_DCHECK` **用量为 0** ——
  所以"只跑 Release 会丢断言"这条经典理由在本仓**不成立**。Debug 唯一的独有覆盖是
  `chq_preview_pump.{h,cpp}` 里 **4 处 `#ifndef NDEBUG`**（`.h:136` + `.cpp:41/57/157`），
  本 ADR **不清理它们**（与 CORE-010「埋点 Release 必须可见」的方向一致，但那是另一张卡的射程）。

### 4. `tools/ci/gate_scope.sh` = 只读路由，把"该验什么"从人脑里搬出来

吃 `git diff --name-only`，吐该跑的窄检命令 + 一句「这趟不需要全量，理由是 X」。**判不准一律升一档**
（宁可多跑一条包测试，不赌漏跑）；映射表逐条带案底（P78/P129/P150、红线、池号）。

## 后果

- **正向**：① 单卡自查从 ≈239s（现有 `--fast`）降到 ≈15s~1min，一天省掉的是"次次数十分钟"；
  ② 全量从"每天可能十几趟"降到"每个版本号一趟"，账上 `version` 列可核；③ 版本号第一次有了真源，
  将来对外发 SDK / 收 podspec 与 Info.plist 时有地方对齐；④ heavy 覆盖点唯一 = 集成机 Release 趟，
  与 ADR-0030 的"集成机是唯一验收口径"自洽。
- **代价（明写，不粉）**：
  ① **heavy 用例在本机 Debug 档从此不跑** —— 若某条硬件链路只在 `-O0` 下坏，本机门禁抓不到；
     缓解有**两层**：`core-rel` 仍全跑 52 例（`-O3`/LTO 只会让 UB 更响不会更静默），
     且 **CI 的 Debug 趟保持全 52 例**（见决定 3 最后一条，它专门留着当 Debug 档覆盖点）。
  ② **全量降频后，P78 类"从未编译过"的代码活得更久** —— 缓解 = L2 合并快检必做且含双壳真编译，
     这层**不许省**（ADR-0030 案底）。
  ③ **路由判错 = 漏跑** —— 缓解 = 不确定就升档 + 映射表每条有案底 + 脚本只读不改状态。
  ④ 版本号引入得**手升**，忘升 = 批账与提交脱节 —— 缓解 = `run_gate.sh` 每趟打印当前版本与
     "本版本已跑过 N 趟全量"。
- **反转条件**：出现一次"heavy 只在 Release 跑 → Release 没跑到的窗口里坏了媒体链路且被用户/真机发现"
  → 恢复"每档全跑"，本 ADR 回滚，代价记进 pitfalls。

## 明确不做（本期）

- **不动 8 份产品 podspec 与两端 pbxproj 的 `s.version`/`MARKETING_VERSION`**（`ChuanqiCutFFmpeg.podspec`
  的 `9.0.2` 是 FFmpeg 上游 pin，与本条无关，不要"顺手统一"）：本 ADR 要的是**批次口径**，
  不是对外发布。改 podspec = 高冲突面 + 双端 `pod install` + 链接层三层取证（P150），
  收益在本期是零。真要做时单独开卡，且必须一次收齐 podspec / pbxproj / `Info.plist` 三处
  （**从 `VERSION` 读**，不再各写字面量）。
- **不引入 `0.x` 以上的大版本、不建发布流程**（无对外发布需求）。
- **不清理 `#ifndef NDEBUG`**（归预览泵那张卡）。
- **真机与问卷节奏不动**（传哲 2026-10-17 明示「这次只管门禁，真机不动」）；
  `VERSIONS.md` 的批账暂不要求每批附真机趟。
- **不给 heavy 用秒数阈值定义**（见决定 3 的第四条）。
