# ADR-0015:相册选择器策略 —— 系统 Picker 过渡、不引三方、B 期自研浏览器

- **状态**:已批准(2026-10-04 用户确认分层路线)
- **日期**:2026-10-04
- **相关**:Spec UIA-011(系统 PhotosPicker 落地)/ Spec UIA-012(多选)/
  Spec UIA-013(自研浏览器)/ ADR-0010(平台基线)/ TASK-UIA-011

## 背景

UIA-011 已用系统 `PhotosPicker`(零依赖、零权限)落地相册视频导入,已知
短板:单选(012 解决)、sheet 不可品牌化、无相簿浏览、无时长过滤、iOS 16
无选择序号。2026-10-04 应"是否有做得好的三方库 / 自研是否可行"的选型问题
做了调研,需要把结论固化,避免后续重复调研与决策漂移。

**调研结论(2026-10-04 时点,star 数为时点数据)**:

| 库 | 活跃度 | 协议 | 结论 |
|---|---|---|---|
| ZLPhotoBrowser | 活跃(v5.0.0,适配 iOS 26/27,~5k★) | Apache-2.0(4.7.4 起,原 MIT) | 质量合格,不引(理由见决策 1) |
| HXPhotoPicker | 活跃(v5.0.5,2025-12,~3.4k★;旧名 HXPHPicker 仓库已归档,勿引错) | MIT | 同上;Picker subspec 模块化干净 |
| AnyImageKit | 停滞(0.6.x 停在 ~2022) | MIT | 不押注 |

平台事实:Android 官方方向是系统 Photo Picker(Android 13+ 内建、Play
services 向下兼容、androidx photopicker 模块,权限政策也在推);鸿蒙官方
入口是系统 PhotoViewPicker,直接读相册需受限 ACL 权限。

## 决策

1. **不引入第三方相册选择器库**(iOS 端 ZL/HX 质量合格也不引)。理由:
   ① 三端不复用 —— Swift 库不会迁移到 Compose/ArkUI,引了就是"iOS 独有的
   第三种相册 UX";② 生态错位 —— 两家核心都是 UIKit,与 SharedUI
   SwiftUI-first 设计系统相抵触;③ 能力冗余 —— 我们只需"选视频",库的
   编辑器/相机/GIF/LivePhoto 约八成能力用不上(相机/编辑自研 CAM-* 覆盖);
   ④ 红线 #10 治理成本(manifest + 协议评审 + SBOM)对单 picker 不划算。
2. **近期(A 期):UIA-012 用系统 PhotosPicker 多选**(`maxSelectionCount`)
   收掉批量导入痛点,维持零权限零依赖。
3. **中期(B 期):UIA-013 自研 SwiftUI 相册浏览器**,替换 UIA-011 挂载点
   (按钮 + item→URL 胶水保留,换选择器本体)。**显式偏离"零权限"惯例**:
   新增 `NSPhotoLibraryUsageDescription` + 隐私标签申报,由 UIA-013 落地。
4. **三端策略:不强行统一相册选择 UI**。iOS 自研组件仅 Apple 端;Android
   用系统 Photo Picker(+官方兼容库);鸿蒙用系统 PhotoViewPicker。三端
   统一的是"选择结果 → `importMedia` → Command 建片段"链路,不是选择器
   的皮。
5. **三方库仅作设计参考**:读 ZLPhotoBrowser / HXPhotoPicker 源码提炼
   PhotoKit 边缘 case 清单(iCloud 未下载、受限相册、慢动作/HEVC、
   缩略图缓存调度等),**不拷代码、不抄依赖**。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 直接引 ZLPhotoBrowser / HXPhotoPicker | 见决策 1 四条理由 |
| A 期直接自研浏览器 | 批量痛点用 `maxSelectionCount` 一天级可收;自研含权限/隐私申报与 PhotoKit 边缘 case,应给 Spec/ADR 流程,不阻塞当前验收节奏 |
| 维持单选不改 | 批量导入是多机位/分镜素材的真实高频路径,单选体验代价随素材量线性增长 |
| 引 AnyImageKit 等停滞库 | 维护风险;新 iOS 版本适配无人跟进 |

## 后果

**正面**
- 过渡期维持零权限、零依赖,隐私与审核成本最低(继承 UIA-011 结论)。
- 调研结论落盘,选型问题不再重复讨论;三方库成为"设计参考清单"而非依赖。
- B 期 UI 完全可控(品牌化、时长过滤、序号徽标),且与素材库整理任务在
  "选中项 → 文件 URL"一步自然汇合。

**负面 / 成本**
- B 期自研要自担 PhotoKit 边缘 case 维护(iCloud、受限模式、大图库性能)。
- 两套选择 UI 并存与切换期(系统 sheet → 自研浏览器),用户需再学习一次。
- 批量多选放大 D3 的 tmp 依赖(重启失效批量出现),素材库整理任务收口前
  是已知限制。

**缓解**
- 边缘 case 清单来自成熟开源库源码(决策 5),不自创踩坑路径。
- 自研浏览器纯逻辑抽可单测类型,PhotoKit 行为差异收敛在数据面层。
- D3 tmp 失效问题在 Spec UIA-012/013 中显式声明为已知限制,不静默。

## 反转条件

- 自研浏览器实测维护成本超预期(PhotoKit 新系统版本适配跟不动、边缘
  case 修复持续失血)→ 重新评估引 HXPhotoPicker Picker subspec(模块化
  最干净、MIT)做 Apple 端兜底,重新过红线 #10 评审。
- Android/鸿蒙官方系统 picker 能力覆盖了品牌化/过滤需求且 iOS 系统
  sheet 对齐该能力 → 可重估"三端全系统 picker"取消自研。

## 落地任务

`TASK-UIA-012`(A 期,系统多选)、`TASK-UIA-013`(B 期伞任务,自研浏览器)。
