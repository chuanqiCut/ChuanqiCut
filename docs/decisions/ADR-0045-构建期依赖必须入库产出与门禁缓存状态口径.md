# ADR-0045：构建期依赖必须有入库产出脚本；"门禁绿"必须标注缓存状态

  其中"本机 SPIRV-Cross 带不入库本地补丁"这一条仍挂在池 [23] 等拍板）
- **日期**：2026-10-17
- **决策者**：集成机（本机 = 唯一验收口径）；事故取证在 INFRA-034 的 CI 复现里
- **依据**：`.ai/memory/pitfalls.md` **P160 / P161 / P162**；`docs/tasks/TASK-INFRA-034.md` §实测

- **相关**：ADR-0029/0030（双机分工与门禁节奏）、ADR-0044（顶层布局，`engine/shaders/` 归位）、

## 背景

SHADER-001（`engine/shaders/portable/blit.{vert,frag}` → glslang → SPIR-V → SPIRV-Cross → MSL）
跑在**编译期**：`engine/platform/apple/CMakeLists.txt` 的 custom command 调
`tools/shaders/build_shaders.py`，后者默认硬要两个第三方二进制
（`build/tools/glslang/StandAlone/glslang`、`build/tools/spirv-cross/spirv-cross`）。

INFRA-034 给 `.github/workflows/ci.yml` 交"本机等价复现证据"时，按 workflow 顺序**真的 `rm -rf build`**，
第一次就炸：

```
[ 27%] SHADER-001: glslang → SPIR-V → spirv-cross → MSL (blit)
error: shader 工具链不可用（试过：…/build/tools/glslang/StandAlone/glslang）
make[1]: *** [engine/platform/apple/CMakeFiles/cq_shaders_msl.dir/all] Error 2
→ ctest rc=8，2% tests passed, 50 tests failed out of 51（全是 Could not find executable）
```

逐条核过（判据只认 `git ls-files` 的入库文件）：**仓库里从来没有产出这两个二进制的脚本** ——
`tools/deps/deps.py` 只有 validate/lock/check/selfcheck（**无 build 子命令**）、`tools/CMakeLists.txt`
是占位 target、`third_party/CMakeLists.txt` 只处理 ffmpeg、`git log` 搜不到产出脚本。
本机那套是历史会话手搓的，源码树 `third_party/src/` 与产物 `build/tools/` 又都在 `.gitignore` 里。

**为什么藏了整整几周**：`tools/ci/run_gate.sh` 的 17 步从不删 `build/tools/`，所以"构建期第三方依赖齐不齐"
**从未进入判据**。这是 P147/P151 那类"暖缓存假绿"的加强版 —— 判据只在暖缓存上跑，缺依赖就等于不存在。

## 决策

1. **任何构建期依赖（编译期要调用的外部二进制/脚本/模型），必须有一个入库脚本能从零产出它。**
   "本机能编"不构成证据：本机可以带着从没登记在仓库里的历史产物。
   落地：`tools/build/build_shader_toolchain.sh`（pin 从 `third_party/manifest.toml` 读，脚本内**不写死
   commit**，避免同一判据两份真源；源码缺失按 `pin_ref` 浅 fetch 并校验 `HEAD == pin`；
   产物齐备后 `glslang --version` / `spirv-cross --help` 自检 + **端到端真转一遍 SHADER-001**）。
2. **交付判据里必须包含"清空产物目录后重跑"**，不能只交暖缓存门禁。
   复刻 CI 用真破坏性动作（`rm -rf build`），增量复现只会复述已知的绿。
3. **今后引用"门禁绿"必须同时说明缓存状态**（暖 / 冷 / 干净复现）。
   `PASS=17` 与本仓 10-16 之前的所有绿都是**暖缓存口径**，不得被引用成"CI 可用"。
   两套数字口径不同、不可互替：全量门禁 10m57s（暖）/ 18m58s（冷）；CI core 段干净复现 6m48s~11min。
4. **CI 里的装配步必须排在内核构建之前**，并写成 workflow 头部的显式约束
   （`build_core.sh --clean` 会把刚装好的 `build/tools/` 一起清掉）。
5. **幂等脚本必须自带残骸清理与只读短路**（P161/P162 引出的三条硬规则）：
   - 产物缺失 ⇒ 视为上次没成功 ⇒ 重配前清掉旧 `CMakeCache.txt`（旧缓存会把上次的 `-D` 值原样端回来）；
   - 自称 `--check-only` / dry-run 的模式**不得包含任何删除**，且必须在**函数入口**短路，
     不是每个副作用点各判一次；
   - grep CMake cache 键时类型段写成可选 `^KEY(:[A-Z]+)?=`（裸 `-D` 落的是 `:UNINITIALIZED=`，
     写死 `:STRING=` = 一条恒不命中的判据）；
   - "两侧各自拼路径"的构建期约定必须在**大小写敏感**的卷上验过：本仓出参目录必须是全小写
     `build/tools/spirv-cross/`，与 `tools/shaders/build_shaders.py:111-113` 的默认查找路径逐字一致
     （macOS 默认 APFS 不区分大小写会"碰巧能用"，Linux runner 上直接"工具链不可用"）。

## 明确没做 / 边界

- **没有把这条写进 `AGENTS.md` 红线**：真源是热点文件、本批已因红线 #6 动过一次，再动会把生成物
  （`CLAUDE.md`/`.cursorrules`/`.windsurfrules` 等 5 份）二次扩大。口径先由本 ADR +
  `docs/BUILD.md` + `.workbuddy/memory/MEMORY.md`「构建期依赖铁律」承担；若传哲要升为红线，
  改真源 + `sync_context.py` 另起一批。
- **pin 级校验仍有一道口子**：本机 `third_party/src/{glslang,SPIRV-Cross}` 是历史 checkout 的**非 git 树**，
  脚本只能做版本级核对并**明打**"commit 级 pin 不可校验"；CI / 新克隆机走 pin 的 `git checkout`，
  那一路才有 `HEAD == pin` 硬判据。
- **池 [23] 未决**：本机 SPIRV-Cross 源码树里带着一处**不入库的本地补丁**（把非 git 树中
  `git describe` 向上抓宿主仓库 HEAD 造成的假版本横幅改成 manifest pin），CI 吃的是未打补丁的上游树
  → 本机与 CI 的依赖**不同源**。接受则把它登记成 `deps.py` 的显式字段，不接受则本机也**始终**按 pin
  做 `git checkout`（`ensure_src` 已有该路径，代价约 25~40s/仓）。

## 验证

| 判据 | 实测（本机 = 集成机，Intel x86_64，cmake 4.4.3） |
|---|---|
| 清空产物根后能从零装配 | `rm -rf build` → `CMAKE_BIN=cmake tools/build/build_shader_toolchain.sh` rc=**0**；glslang **3 133 560 B**、spirv-cross **4 155 984 B**、`blit_msl.h` **1689 B** |
| CI core 段连续 2 次绿 + 排除名单可见 | run3 与 run4：toolchain/build/ctest 全 rc=**0**、**51/51**，日志显式打印 `Test #45: platform_apple_decode` |
| 幂等（暖跑不重复劳动） | 两工具均 `产物已存在，跳过编译`，"强制重编"零行 |
| 只读模式不破坏现场 | 暖态 `--check-only` rc=**0** 且 `spirv-cross` md5 跑前后逐字节一致 |
| 负向（产物缺失必须红） | 挪走 `build/tools/glslang/StandAlone/glslang` → `--check-only` rc=**1**、报 `产物缺失`；恢复后 rc=**0** |
| 装配顺序 | `ci.yml` 内核构建前一步跑本脚本；`build_core.sh` 不再自行拉取第三方 |

## 修订 R1（2026-10-17 同日，传哲复核池 [23]）

- **状态变化**：头部「待传哲在同一轮复核」→ **已复核**。除池 [23] 一条外，ADR 正文与判据不变。
- **池 [23] 拍板 = 「具体事务具体分析」**：不为"版本横幅归属"这一处去改造依赖治理
  （不引入 `deps.py` 的"本地补丁存在"字段，也不把本机树强制重取成 pin 的 git checkout）。
  本 ADR 的**铁律本身不受影响**：构建期第三方工具**必须有入库产出脚本**（glslang/SPIRV-Cross 已由
  `tools/build/build_shader_toolchain.sh` 产出，这条是绿的）；被裁掉的只是"对本机不可分发补丁做统一登记"这一层。
- **仍然成立的口径**（裁定不豁免它）：本机与非 git 树的版本横幅来自那处补丁，CI / 新克隆来自真 git 树，
  **两条证据来源不同**，任何一侧的版本号都不能指认另一侧、更不能指认 ChuanqiCut 的 commit。
- **下次同类事故的分诊问句**（把"具体分析"变成可执行的三步）：
  1. 这个本地改动**影响产物正确性**还是只影响**日志可读性**？（本条=后者）
  2. 入库产出的代价能不能被一次构建吸收？（能 → 入库；不能 → 按案）
  3. 不入库时，判据能不能**看见**它？（能 → 保持开放 + 本池条目；不能 → 必须先补判据再谈容忍）
