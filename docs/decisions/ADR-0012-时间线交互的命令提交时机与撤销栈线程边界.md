# ADR-0012：时间线交互的命令提交时机与撤销栈线程边界

- 状态：已接受
- 日期：2026-10-03
- 相关任务：UIA-005（拖拽/裁剪交互）、UIA-008（Undo/Redo 入口）、MODEL-002
- 影响面：`cq_sdk.h`（新 ABI 6 个）、`EditorModelState`、SharedUI 时间线交互

## 背景

UIA-005 要解决「片段拖拽/裁剪」与「撤销/重做」两件事，二者共享同一个底层
问题：**命令什么时候进 CommandHistory，以及谁在读它的状态**。

HANDOFF-003 留的设想是「拖拽连续命令合并（coalescing）届时设计」——
即默认拖拽会持续产生命令，需要事后合并。本 ADR 推翻这个前提。

## 决策

### D1：拖拽期间不提交，松手时提交**一条**命令（不引入 coalescing）

- 拖拽中的几何变化是 **UI 本地状态**（`ClipDrag` + `ClipPreviewOverride`），
  不进模型、不进历史。
- 松手时提交一条 `MoveClipCommand` / `TrimClipCommand`。

理由：需要 coalescing 的前提是「每帧都提交」。而每帧提交本身就是错的 ——
一次拖拽会产生几十条中间态命令，Undo 栈被污染（用户按一次 Cmd+Z 只回退
几像素）。**取消掉需求来源，机制就不必存在**。

代价：拖拽期间预览画面走本地几何（与内核不同步），松手前内核模型不变。
这是可接受的 —— 预览渲染读的是内核快照，拖拽位移只影响时间线的矩形绘制。

### D2：提交后必须主动回查内核真值

内核可能拒绝（同轨重叠 / duration ≤ 0），而**拒绝不触发 observer 回流**。
若 UI 保留本地预览位置，就会显示一个内核里不存在的「幽灵片段」。
故 `commit()` 后一律调 `refreshFromKernel()`。

代价：提交成功时会有一次旧值回弹（observer 随后刷到新值）。**正确性优先
于动画平滑** —— 幽灵片段比闪一下严重得多。

### D3：Undo/Redo 也是 session 线程操作，必须异步入队

`CommandHistory` 非线程安全，且它翻的是 `Timeline` —— 两者都是 session
线程状态。故 `cq_session_undo/redo` 与 add/move/trim 同构：**Ok = 已入队**，
空历史在 session 线程返回失败（表现为版本不推进）。

### D4：撤销栈能力标志走原子量，UI 不得直读 CommandHistory

`EditorModelState` 维护 `atomic<bool> can_undo_ / can_redo_`，由
Execute/Undo/Redo 成功后刷新（`RefreshHistoryFlags()`）。
`cq_session_can_undo/can_redo` 同步读这两个原子量（任意线程、不阻塞）。

⚠️ 返回值是**数据**（0/1）不是状态码 —— 与 `cq_is_main_thread` 同族，
不要拿去比 `cq_status_is_ok`（P26）。

### D5：裁剪只做右边缘（改 duration）

`TrimClipCommand` 的语义是「只改 duration，不动 source_in」（MODEL-002 定）。
左边缘裁剪需要同时改 start + source_in + duration，是**另一条命令**，本期
不提供。UI 上左边缘归「移动」，不出现裁剪手柄。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 拖拽每帧提交 + coalescing 合并 | Undo 栈污染是合并机制救不回来的（合并时机、合并键都靠猜）；取消每帧提交更干净 |
| 撤销在调用线程同步执行 | CommandHistory 非线程安全；同步执行会让 UI 线程阻塞在模型操作上（违反红线 #8） |
| UI 直读 CommandHistory::CanUndo | 跨线程读非线程安全状态；必须走原子标志 |
| 提交被拒后靠 observer 纠正 | 拒绝不触发 observer，UI 无从得知 |
