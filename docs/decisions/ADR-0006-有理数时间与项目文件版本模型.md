# ADR-0006：有理数时间模型与项目文件版本化

- **状态**：提案（待批准）
- **日期**：2026-09-23
- **相关**：RESEARCH-001 F10、ARCH-001 §5

## 背景

原调研（`技术调研_关键架构补遗.md` §1.3）的项目文件示例中，时间用**浮点秒**表示：

```json
"duration": 120.0,
"sourceRange": {"start": 10.0, "end": 30.0}
```

浮点秒无法精确表示 NTSC 帧率（23.976 / 29.97 fps）。累积误差会导致：帧漂移、音画不同步、导出帧数偏差。这是会在项目后期才暴露、且极难定位的 bug 类型。

同时，项目文件需要跨 iOS/macOS/Android 打开，必须有版本机制。

## 决策

### 1. 有理数时间

```cpp
struct RationalTime {
    int64_t value;       // 以 timescale 为单位的整数
    int32_t timescale;   // 每秒刻度数，> 0
};
```

- **禁止在任何持久化数据、跨模块接口中使用浮点秒**。
- 项目 timescale 统一取 **60000**（可被 24/25/30/60/1001 整除，覆盖主要帧率）。
- 素材保留其原生 timescale，转换只在边界发生一次。
- 加减乘除做 timescale 归一化并检测溢出；序列化为 `{ "value": N, "timescale": M }`。
- 单测必须覆盖：29.97fps 下累计 10000 次帧步进后无漂移。

### 2. 三套时间坐标

| 坐标 | 定义 |
|---|---|
| TimelineTime | 时间线上的位置 |
| SourceTime | 素材内部位置（由 `TimeMap` 从 TimelineTime 映射） |
| PresentationTime | 输出时间线位置，用于编码时间戳与音画同步 |

`TimeMap` 是 Retime 的唯一抽象，恒速 / 速度曲线 / 倒放三个实现同一接口（对应 RESEARCH-001 C6）。

### 3. 项目文件版本化

```
Project.chuanqicut/
├── manifest.json        # { schema_version, app_version, created, modified, ... }
├── project.json         # 时间线数据（有理数时间）
├── undo_history/        # 可丢弃
├── assets/              # 媒体（软引用或拷贝）
└── cache/               # 缩略图 / 波形，可丢弃重建
```

- `schema_version` 为整数，单调递增。
- **迁移器链**：`Migrator_v1_to_v2`、`Migrator_v2_to_v3` …，打开旧项目时按顺序执行到当前版本。
- 迁移必须可测试：为每个 migrator 提供旧版本样本文件，CI 验证迁移结果。
- 打开更高版本的项目必须明确报错，不得静默降级解析。
- 自动保存：先写临时文件再原子替换（原调研这条结论正确，采纳）。

### 4. 跨端兼容

- 序列化格式与字节序、路径分隔符、数值精度在 schema 中明确定义。
- 媒体引用使用**相对路径 + 资产 ID**，禁止绝对路径（否则跨设备/跨端打不开）。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 浮点秒 | NTSC 精度丢失，帧漂移 |
| 平台原生时间类型（CMTime） | 只能在 Apple 用，无法跨端，也无法持久化到共享 schema |
| Protobuf / FlatBuffers | 体积与性能优势在当前规模下不构成收益，且降低可读性与调试效率 |
| 无版本迁移，直接兼容 | 跨端跨版本必然出现格式演进，无迁移机制等于埋雷 |

## 后果

**正面**
- 消除一类难以定位的时间漂移 bug
- 跨端打开项目文件有确定性行为
- 迁移路径可测试、可审计

**负面 / 成本**
- 有理数运算的实现与单测成本高于浮点
- 迁移器链需要长期维护（每个 schema 变更都要写 migrator + 样本）

## 反转条件
无。这是不可妥协的基础设施决策。

## 落地任务
