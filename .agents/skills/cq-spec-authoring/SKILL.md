# Spec 编写

## 触发
新需求 / 范围不清 / 需求直接以"做个功能"的形式出现。

## 流程
1. **先分类**：这是编辑能力？效果能力？平台适配？性能/稳定性？基建？
2. **读既有事实**：`.ai/modules/<模块>.md`、相关 `docs/decisions/ADR-*.md`、`.ai/memory/baselines.md`
3. **问清四件事**（问不出来就写"开放问题"而不是猜）：
   - 用户价值与成功行为是什么
   - 影响哪些模块（写进 read_set）
   - 哪些约束不可违反（对照 AGENTS.md 的 10 条架构红线）
   - **如何观察成功或失败**（这是最容易漏的）
4. **写非目标**：明确不做什么，比写做什么更能防止范围膨胀
5. **定验收**：可观察、可机器判定。禁止"体验流畅""效果自然"这类不可判定表述

## 检查清单
- [ ] 目标与非目标都写了
- [ ] 验收标准可机器判定（有数字、有命令）
- [ ] 影响模块已列出，且已读对应 `.ai/modules/`
- [ ] 不违反 10 条架构红线
- [ ] 开放问题单列，没有被悄悄假设掉
- [ ] 跨端影响已考虑（iOS/Android/鸿蒙 各自是否需要、行为是否一致）

## 输出
写入 `docs/specs/SPEC-<ID>.md`，使用 `.ai/templates/spec.md` 模板。
结尾给出：下一步应调用 `cq-task-planning`。
